# investigating-domain

## 目的

コードや設定へ分散した業務知識を復元し、次の問いに答える。

> 誰または何が、どの条件で何を行え、どの業務ルールによって状態や関係が変わり、何が守られるか。

画面、ディレクトリ、レイヤーなどの構造は前提にしない。純粋なcall graphや一般的な障害経路だけの調査は対象外とし、業務上の意味や制約を確認するために必要な範囲で扱う。

## 実行手順

1. **ドメイン調査の範囲を定める**
   - 初見の読者へ説明するため、対象システムが誰のどんな業務を支え、今回の対象がその中でどこに位置するかを確認する。
   - 元の依頼を、対象とする業務概念または業務フロー、知りたい仕様、影響境界、対象外へ言い換える。
   - 業務用語、関係者・ロール、データの関係、状態、ルール、不変条件、ワークフローを暫定的な仮説として挙げる。
   - 各仮説を確認できる実装、設定、契約・スキーマ、DB制約、テスト、履歴、実行時証拠を理由付きで特定する。
   - この段階では仮説を結論にせず、調査対象と未確認点を確定する。
   - 分担が有効な場合だけ、独立した業務フロー・境界・問いごとに分ける。最終的な範囲と統合は主担当が保持する。

2. **ドメインの証拠を集める**
   - 業務用語とデータの意味、関係、所有者を確認する。
   - 関係者ごとに、許可・拒否される操作、その前提条件、適用される業務ルールを確認する。
   - 状態ごとに、遷移の契機と条件、禁止される遷移、状態変化に伴う副作用を確認する。
   - 業務フローを、起点、判断、状態変化、他の関係者やシステムへの引き渡し、結果または業務上の失敗の順で追う。
   - 不変条件が実装、設定、契約・スキーマ、DB制約、テスト、実行時のどこで保証されるか確認する。名称や検索結果だけで判断しない。
   - 各重要な主張を「事実」「事実からの推論」「未確認」に分け、再確認できる根拠の場所を付ける。矛盾する証拠は消さずに残す。

3. **業務知識として統合する**
   - まず対象システムの目的、主な利用者、対象業務の位置づけを短く説明し、その後で元の調査質問へ回答する。
   - 用語・概念・データの関係、関係者と権限、ルールと前提条件、不変条件を整理する。
   - 状態遷移と業務フローを順序立て、正常な結果、業務上の拒否・失敗、副作用を示す。
   - 実装、設定、契約・スキーマ、DB制約、テスト、実行時証拠の一致・不一致と未確認点を示す。
   - 影響調査では、変更する業務ルールを起点に、データ、契約、利用者、テスト、運用への波及を示す。
   - 重要な主張には証拠を添え、事実・推論・未確認を混ぜない。複数の条件、関係者、状態の差が文章だけでは分かりにくい場合に限り、表や図を使う。
   - 「そもそも何のためのシステムか」「今回の対象がどの業務を担うか」「誰が、どの条件で、何をできるか」「何がどう変化し、何が守られるか」「重要な主張をどの証拠で確認したか」を説明できることを完了条件とする。

問いの再設定、広い原因仮説の発散、反証、次の検証設計が必要な場合だけ、`hypothesis-framing` に引き渡す。業務知識の復元と証拠の統合はこのスキルで完了させる。
