# Explain Change Impact

AIが実装を終えることだけを目的にせず、ユーザーが変更を判断できる説明面を保ちながら開発する。
「説明した」「OKを受けた」を理解済みの証拠にしない。記録するのは、提示した事実、ユーザーが訂正した内容、選択した案、承認した変更境界である。

ユーザーがskill名を指定するのを待たない。通常の実装依頼でも、状態、所有、外部contract、複数entrypoint・consumerへ波及すると確認した時点でこのworkflowへ切り替える。

テンプレートが必要なときは[templates.md](references/templates.md)を読む。

## 1. 発動レベルを決める

作業開始時に、変更を次のいずれかへ分類する。

| レベル | 条件 | 進め方 |
|---|---|---|
| 通常 | contractを変えない局所変更。誤字、format、単一箇所の表示調整など | 短い説明後、そのまま進める |
| briefing必須 | 複数component・entrypoint・consumerへ波及する。状態、非同期処理、失敗経路を変える | 実装前briefingを提示してから進める |
| decision待ち | architecture、process、resource所有、外部・永続contract、製品上の不変条件を変更する | 既存Issueや依頼で決定済みでなければ、選択・訂正を受けるまで実装しない |

途中で範囲が広がったら再分類する。曖昧な「大きな変更」ではなく、境界、状態、所有、contract、consumerの変化で判断する。

## 2. 現行動作を原典から確認する

リポジトリの`AGENTS.md`、architecture文書、feature map、Issue、利用箇所、テストを読む。PR本文や設計案だけで現行動作を補わない。

ユーザー操作から開始し、次の順に追う。

1. 誰が、どの入口から操作するか。
2. どの境界、process、adapterを通るか。
3. どの状態とresourceが変化するか。
4. どの外部I/O、保存結果、通知へ到達するか。
5. 正常終了と失敗時にresourceを誰が回収するか。

コードの事実収集が必要なら`investigating-domain`を使う。事実、推論、提案、未確認事項を分ける。

## 3. 実装前briefingを提示する

ユーザーが差分を読む前に判断できるよう、まず次の俯瞰だけを1画面程度で提示する。

1. 現在はどう動くか。
2. 何を変え、何を変えないか。
3. 壊してはいけない条件と、未決定の判断点。

一度に全ファイルや全contractを列挙しない。重要な経路は小さな図、重要な不変条件は3〜7件へ絞る。根拠ファイル、完全な影響map、失敗経路などの詳細は、その後に必要な分だけ示す。専門用語を初めて使うときは、今回の文脈で何を指すのかを短く添える。

俯瞰の後、必要に応じて次を示す。

- 現在の動作: ユーザー操作から副作用までの経路。
- 変更後の動作: 所有者、境界、状態遷移がどう変わるか。
- 変更する範囲と変更しない範囲。
- 影響map: contract、producer、consumer、別入口、失敗経路、文書、テスト。
- 不変条件: 番号、内容、種別、根拠または決定者、検証方法。
- 未確認事項と、ユーザーが決める必要のある選択肢。

図は関係を理解しやすくするときだけ使う。3つ以上の境界はflowchart、時系列はsequence、相互排他的な状態はstate、resource所有は表を優先する。

## 4. 不変条件と決定を分ける

各条件を次の種別に分ける。

- `既存`: 仕様、コード、テスト、運用から確認した条件。
- `維持案`: 今回も守るべきだとagentが提案する条件。
- `変更候補`: 意図的に変える可能性がある条件。
- `未確認`: 根拠または期待が確認できていない条件。

既存条件の発見と、製品判断として新しく決める条件を混同しない。ユーザー判断が必要なものは`D1`のようにdecision IDを付け、選択肢ごとにどの不変条件へ影響するかを示す。

## 5. 理解checkpointを作る

クイズや「理解しましたか」という質問をしない。ユーザーが訂正・選択しやすい判断面だけを提示する。

```text
維持する条件: I1, I2
変更候補: I3
未決定: D1 = A / B
各案がI1-I3へ与える影響: ...
```

返答例も短く示せる。

```text
- I1/I2を維持し、D1=Aで進める
- I2の理解を修正: ...
- D1を決める前にresource解放経路を詳しく
```

Issueや明示依頼ですでに決定済みなら追加承認を求めない。根拠を示して進める。

## 6. 実装中も説明を同期する

commentaryではtool実行ログを並べず、判断に必要な変化を次の形で報告する。

```text
新事実: ...
影響: I2 / D1 / scope
判断: 続行 / briefing更新 / decision待ち
```

briefingを崩す新事実が見つかったら、矛盾する実装を止める。scope、不変条件、選択肢を更新し、decision待ちに該当する場合はユーザーへ戻す。

複数agentを使う場合も、main/coordinatorがbriefingと決定記録を所有する。workerにscopeや不変条件の変更を独断で許可しない。

## 7. 実差分から影響を再確認する

実装後は事前予測をそのまま報告しない。実差分の変更対象、定義元、全利用箇所、別入口、fixture、文書、テストを検索し直す。必要なら`review-impact-analysis`を使う。

次を確認する。

- 予定外に変更した境界やcontract。
- 予定していたが変更しなかった箇所。
- 新しく判明したconsumerと失敗経路。
- 各不変条件を直接検証する証拠。
- 未実行、実機依存、環境制約などの未検証領域。

一般的なbuild成功を、不変条件を直接確認する証拠として代用しない。

## 8. handoffとPRへ残す

最終報告とPR本文には、次を残す。

1. 実際に変わった動作。
2. currentとtarget、または予定と実績の差。
3. 実差分から確定した影響map。
4. 不変条件と検証証拠の対応。
5. 未検証領域と、ユーザーが追加確認すべき判断点。

設計成立性が重要なら実装前に`design-review`、実装後の通常レビューには`review`、反例探索には`adversarial-review`、PR作成には`create-pull-request`を組み合わせる。

## 完了条件

コードとQCが完了していても、非自明な変更で次が欠けていれば完了扱いにしない。

- ユーザーが判断できるcurrent/targetの説明。
- 実差分に基づく影響map。
- 不変条件と検証証拠の対応。
- 未確認事項と未検証領域の明示。
