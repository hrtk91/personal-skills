# フロントエンド開発

フロントエンドの実装では、先に「何が起きる画面なのか」と「その状態を誰が持つのか」を決める。その後でUI、状態管理、外部システムとの境界を配置する。React、Vue、Svelteなどのフレームワーク固有の書き方は、この原則を実現する手段として選ぶ。

## 1. 表示・データ準備・変更要求の責務を分ける

`view = f(state)`を基本にする。Viewは渡された状態を表示し、ユーザーの操作を意味のある要求として通知する。表示用データの取得や業務フローをViewへ埋め込まない。

画面の入口には、次の二つの責務を置く。ここでいう入口は、画面とアプリケーションの処理を接続する境界であり、特定のファイル名やクラスを要求するものではない。

- **表示データの準備**: URLなどから対象を解決し、表示に必要なデータとリソースの参照先を取得・構成してViewへ渡す。
- **変更要求の受付**: UIからの入力を検証・変換して業務処理へ委譲し、結果を返す。変更後は表示データを再取得するなど、正本と表示を一致させる。

業務上の操作可否・計算・遷移条件と、複数の処理を進める業務フローは、UIや画面入口の仕組みから独立した関数や型に置く。画面入口はそれらを呼び出す。controller、viewmodel、usecaseという層名は必須にしないが、業務処理をUIフレームワークなしで実行・検証できる境界を保つ。

### フレームワークへの対応づけ

まず採用しているフレームワークのデータ取得・変更・再取得の仕組みを、この二つの責務へ対応づける。componentや独自hookで同じ仕組みを作る前に、既存の画面入口で扱えるか確認する。同等の仕組みがない場合も、二つの入口を明示して接続方式を揃える。

例えばRemix / React Routerのloader・clientLoaderは、ルートに対応する表示データを準備して画面へ渡す処理である。route actionは変更要求を受け付ける処理であり、Form・fetcherなどの送信手段と、変更後のデータの再検証・再取得を組み合わせて使う。これらを利用できる構成では第一選択とし、取得済みデータをhookのlocal stateへコピーして独自に更新しない。

## 2. 状態の正本と寿命を決める

一覧の選択、音声再生、文字起こし、編集など、関心ごとに状態の所有者を一つ決める。関係のない状態を巨大な一つのstateにまとめない。既にrouter、form、データ取得library、外部APIなどが管理している事実は、その状態から導出し、propsやlocal stateへ正本を重複させない。URLの対象解決や初期データの取得は画面入口で扱う。

入力途中の値やダイアログ開閉など、UIと一緒に消えてよい単純な値はlocal stateで扱ってよい。画面を閉じても継続すべき業務処理は、componentのmountや購読の有無に依存させない。

hookやcomposableは、状態をUIへ接続し、再生制御・購読・cleanupなどUI側のリソースの寿命を扱う実装手段である。表示データの準備や業務フローを無条件に置く場所にはしない。

例えば既存録音の表示では、画面入口で文字起こしの内容と再生用URLなどを準備する。文字表示は内容を描画し、プレイヤーは再生・停止・シーク・バッファリングを管理する。音声本体の一括取得まで画面入口へ要求しない。解放が必要な一時URLやライブ購読などは、生成から解放までの所有者を明示する。

## 3. アプリケーションが持つ状態と遷移を明示する

前節までで決めた所有者のうち、アプリケーション自身が管理する状態について、有効な状態・イベント・遷移を定義する。effect、watcher、refを書き始める前に、各イベントを確定できる状態源を確認する。複数の値の変化から「処理が始まったはず」と推測しない。

### 状態の表現

同じ軸で排他的な業務状態は、状態の種類と必要なデータを一緒に表し、nullや複数のbooleanの組み合わせから推測しない。TypeScriptならdiscriminated unionを使う。

```ts
type ResourceState =
  | { status: 'loading'; targetId: string }
  | { status: 'ready'; targetId: string; value: string }
  | { status: 'error'; targetId: string; message: string };
```

Viewは状態の種類から描画を分岐する。対象がないことが親の状態なら親が空状態を表し、対象が必要な子には非nullのpropsを渡す。

### reducerを使う条件と責務

画面入口のデータ管理や既存libraryで扱われる状態に、独自の状態機械を重ねない。それでもアプリケーションが所有する複数イベントの状態更新が散らばり、遷移をまとめる必要がある場合にreducerを使う。単純な値や表示だけのUIには要求しない。

reducerは現在の状態とイベント（action）から次の状態を返す純粋な関数であり、データ取得や変更要求の入口の代替ではない。通信や業務フローを実行させない。reducerのactionは状態更新への入力であり、前述のroute actionとは異なる。

画面stateのreducerは、表示対象と取得結果の一致など画面の整合性を守る。業務側の判断を表示に利用しても、操作可否などの業務ルールを各caseへ再実装せず、独立した関数や型へ委譲する。UIイベントは境界で意味のあるイベントへ変換する。

許可されない業務操作は黙って無視せず、操作を受け付ける処理から型付きエラーを返すか、拒否の結果を後から扱える状態へ反映する。呼び出し側への操作結果とreducerが返す次のstateを混同しない。

## adapterで外部I/Oを分ける

外部通信は、差し替え可能なport（interface）を通して行います。adapterはportの実装であり、API、platform service、storageなどとの通信を担当します。adapterに業務状態や画面の判断を持たせません。外部payloadとerrorは、この型付きの境界で変換します。

```text
表示データ: データ準備の入口 → 独立した取得処理 → port → adapter → 外部システム
変更要求: View → 変更要求の入口 → 独立した業務処理 → port → adapter → 外部システム
```

外部I/Oを呼ぶ処理は具体的なadapterではなくportに依存させます。テストではFakeやStubを差し替えられるようにします。ただし、差し替える必要のない単純な処理まで、形式的にadapterへ分けないでください。

外部のWidgetやbrowser APIを組み込む場合は、script読込、型定義、生成、更新、破棄を独自実装する前に、公式SDKと公式資料で案内されるlibraryを確認する。既存libraryへ任せる範囲と、アプリケーションが持つ状態・業務イベント・入力値を分ける。独自実装は、既存の選択肢で必要な契約を満たせない場合に限る。

## 非同期処理と副作用

- 外部API、platform service、audio要素、Blob URL、timer、storageなどを扱う場合は、先に`unavailable`、`loading`、`ready`、`error`などの状態を決める。
- 表示データの取得と変更要求は画面入口で扱う。UI側のリソース制御は、そのリソースを所有するcomponent、専用hook、composableなどに置く。
- propsやstateを外部システムへ同期する仕組みを使う。Reactなら`useEffect`がその手段になる。親が子のフラグを監視して、別の業務処理を開始する用途には使わない。
- 同期処理の依存値には、外部リソースを特定する値を含める。`key`による暗黙の再初期化や、空の依存配列で処理順序を隠さない。
- 非同期処理のcleanupで、購読解除、object URL解放、timer停止などを行う。
- 対象AからBへ切り替えたあと、遅れて返ったAの応答でBを上書きしない。古い応答は業務エラーにせず破棄し、必要な場合だけログや計測へ残す。

## featureの構成

新しく構成を決める場合は、業務featureごとに関連する処理を近くへ置く。既存コードの変更では、その構成と理由を確認し、今回の問題を解決するために必要な範囲で見直す。

```text
src/features/
  recordings/
    components/       # UI component/view
    state/            # union、reducer、状態導出
    adapters/         # 外部APIやplatform serviceとの境界
    tests/
```

feature内に独立した関心ごとが増えたら、`recording-library/`、`audio-replay/`、`transcription/`のようなsub-featureへ分ける。その中も同じ方針で、UI、state、外部境界を整理する。Reactなら`hooks/`、Vueなら`composables/`を、UIと状態を接着する実装の置き場として使う。union、reducer、状態導出、テストは所有する関心ごとの近くに置く。空のディレクトリや早すぎる分割は避ける。

## 最低限の確認

- 業務判断と主要な状態遷移を、それぞれの所有者でテストする。reducerを使う場合は、その状態更新も確認する
- 対象AからBへ切り替えたあと、Aの応答が返ってきてもBを上書きしないことをテストする
- データ準備の入口で対象解決・取得結果、変更要求の入口で成功・拒否・失敗と変更後の表示への反映を確認する
- 入力、ナビゲーション情報、初期データからの状態導出をテストする
- 外部境界のcleanupとerrorを確認する
- 外部統合では、読込失敗、通信失敗、無効な応答、期限切れ、再実行、画面離脱など、該当するライフサイクルを確認する
- buildとfeatureのunit testを実行する

レビューでは、次の5点を確認する。

1. この状態の所有者は誰か
2. 有効な状態とイベントは何か
3. 不可能な組み合わせを型で表せないか
4. 副作用はリソースの所有者にあるか
5. UIを`view = f(state)`として説明できるか。表示データの準備・変更要求の受付をcomponentやhookへ分散させていないか
