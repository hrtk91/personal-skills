# 命名一貫性レビュー

1. 変更差分で追加・変更された関数を先に列挙し、定義本体を隠して呼び出し側の表記だけを読む。
2. 第一チェックとして、各関数名が業務意図を表しているか確認する。
   - 業務ロジックを担う関数は、誰または何を対象に、どの業務操作・判断を行い、何を結果として得るかを名前から説明できる
   - `process`、`handle`、`execute`、`update`、`check`のような汎用動詞や、click、timer、channelなど実装手段だけに業務意図を隠していない
   - UIイベントhandlerでも、`handleClick`ではなく、その操作が開始する業務イベントを表している
   - Application/Domainの関数名が、画面部品、通信方式、永続化方式など外部詳細の語彙へ引きずられていない
   - Infrastructureや描画専用の関数は技術的意図を表してよいが、業務判断を内包するなら業務名へ分離する
   - 名前だけで業務意図を説明できず本体を読まないと分からない場合は、最初の指摘候補にする
3. 次に、変更された型、変数、テスト、テストhelperを列挙し、公開範囲にかかわらず名前と利用箇所を読む。
4. 関数を含むすべての名前について、次を確認する。
   - モジュール名や型名を含む呼び出し表記から、対象、操作または判定、返る結果を説明できる
   - 実装手段の名前だけでなく、利用側が必要とする結果を表している
   - 一覧か単一値か、名前か値かなど、利用側の判断に必要な結果の違いが読める
   - 真偽値を返す処理は、成立条件が名前から読め、利用側で否定が重ならない
   - 同じ概念に既存と同じ用語を使う
   - レイヤー、外部インターフェース、画面、文書をまたいで同じ概念の用語が揃っている
   - ファイル名、型名、関数名、テスト名が同じ責務や仕様を指している
   - `test`、`fixture`、`stub`など役割を示す語が、テストケース、データ、依存生成など実際の役割と一致している
   - 一つの名前が一つの業務上の責任や能力を表し、複数の関心を曖昧にまとめていない
   - 言語に存在しない概念を名前へ持ち込まない
   - 名前だけでは説明できず実装を読んで推測する必要がある場合は、対象、操作、結果のうち不足している要素を特定する
5. 指摘は業務意図を読めない関数名を先に並べ、その後にその他の命名不整合を並べる。各指摘に根拠となるファイルと行、想定される影響、修正案を返す。重大度は親reviewが統一基準で決める。問題がなければ「問題なし」と返す。
