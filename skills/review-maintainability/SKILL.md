# 保守性レビュー

保守性とは、将来の変更・調査・障害対応を、狭い範囲の理解と変更で安全に行えることとする。

「より綺麗に書ける」「さらに抽象化できる」「一般的なパターンを適用できる」という理由だけでは指摘しない。現在の変更や現実的な将来変更に対して、理解範囲、変更箇所、誤変更の可能性、検証コスト、削除コストが具体的に増える場合だけ保守性の問題として扱う。

修正案によって増えるコード、概念、抽象化、テスト、運用責任も保守コストとして評価する。問題より大きい仕組みを追加しない。

## 手順

### 1. 変更された機能・振る舞いを特定する

差分をファイル単位ではなく、変更理由や利用側から見える振る舞いの単位へ分ける。

例:

- 回答を保存する
- 認可条件を変更する
- 外部APIから取得した情報を同期する
- 不要になった機能を削除する

一つのファイルに複数の機能があれば分ける。複数ファイルにまたがっていても、一つの振る舞いなら一つの単位として扱う。

### 2. 各機能の経路を浅く把握する

各機能について、必要な範囲だけ次を確認する。

- 入口
- 業務上の判断や主要な状態遷移
- 永続化や外部I/O
- 外から確認できる結果
- 関連するテスト
- 同種の既存実装や適用されるプロジェクト規約

この段階では、観点ごとにリポジトリ全体を広く探索しない。まず一つの機能を入口から出口まで追える地図を作る。

### 3. 一つの機能ずつ深掘りする

一つの機能について入口から出口まで追い、次の5観点を確認する。終わってから次の機能へ進む。

#### 1. 意図が読める

コードから「何をしているか」だけでなく、「どの業務上の判断や契約を表しているか」を追えるか確認する。

確認すること:

- 名前が実装手段だけでなく、利用側や業務上の意味を表している
- 主要な判断、変換、保存などの段階が追える
- トップレベルの処理から、詳細をすべて読まなくても全体の流れを説明できる
- コメントは実装を言い換えるのではなく、理由、制約、順序の根拠を補っている
- 一度に多くの値を分解したり中間変数を削ったりした結果、値の意味や処理段階を追いにくくしていない
- テストhelperやfixtureが、検証している仕様と前提を隠していない

関数の長さ、ネストの深さ、helperの数だけでは指摘しない。それらによって業務意図や変更箇所を追えなくなる場合に限って根拠として使う。

#### 2. 変更が局所化されている

一つの仕様変更を行うとき、変更箇所を予測でき、無関係な場所まで同期して直す必要がないか確認する。

確認すること:

- 同じ業務ルール、変換、状態判断が複数箇所へ複製されていない
- 変更理由が異なる処理を、一つの巨大な責務へまとめていない
- 外部I/Oや具体的な技術詳細の変更が、必要以上に上位の業務処理へ漏れない
- 境界を越えるデータの表現と変換方法が一貫している
- 設定値、機能切り替え、環境変数の変更箇所が予測できる
- 抽象化は、現在存在する複数の利用側や変更理由を分離するために使われている

実装も用途も一つしかないものに、将来使うかもしれないという理由だけで抽象化を要求しない。重複も、同じ変更で同期修正が必要になるなど具体的な変更コストがある場合に指摘する。

#### 3. 構造が予測可能である

同種の問題を、既存コードや広く知られた慣習から予測できる形で解いているか確認する。

確認すること:

- 同種の既存機能と、責務の置き場所、命名、エラーハンドリング、データ変換の考え方が揃っている
- 独自の設計規則を増やす場合、その必要性を現在の制約から説明できる
- 一般的な設計パターンを使う場合、それによって理解や変更が容易になっている
- 外部サービスとの統合では、公式SDKや公式資料で案内されるlibraryが担える型、通信、生成、更新、cleanupを不要に独自実装していない
- エラーハンドリング、ログ、外部へ返す状態やメッセージが既存パターンに揃っている

既存パターンや有名な設計パターンを適用していること自体を評価しない。予測可能性を上げる場合だけ価値があるものとして扱う。

#### 4. 変更を安全に検証・診断できる

変更後に正しさを確認でき、失敗時に原因と影響範囲を追えるか確認する。

確認すること:

- 変更する振る舞いと、それを守るテストや確認方法の対応が分かる
- 外部I/O、状態遷移、失敗時の流れが追える
- エラーが握りつぶされず、利用側が必要な失敗を観測できる
- resource、process、thread、Actor、connection、lockの所有者と生存期間が読み取れる
- 複数resourceの取得途中で失敗しても、先に確保したresourceを解放できる
- cleanup失敗後もresourceを観測でき、再試行または漏れの検知ができる
- 設定値や環境差による挙動を再現・確認できる

テストの数を増やすこと自体は目的にしない。どの変更や障害を検出する必要があるかは `review-test-quality` の判断に従う。

#### 5. 不要なものを安全に削除できる

機能、経路、設定、resourceが不要になったとき、どこまで消せばよいか予測できるか確認する。

確認すること:

- 機能の入口、主要処理、永続化、設定、テストの境界が追える
- 不要な機能を削除するとき、無関係な機能まで壊す共有状態や責務混在がない
- 変化しやすい情報が正本へ集約され、複製された設定や説明を大量に探して消す必要がない
- 未使用コード、不要なコメント、古いTODO、実装と食い違う説明が残っていない
- 互換層、feature flag、暫定設定など、一時的な仕組みの終了条件や所有者を追える
- resourceや外部連携を削除するとき、生成、利用、cleanupの経路を漏れなく特定できる

削除のためだけに新しい抽象化を要求しない。現実的に削除や置換が見込まれる境界で、現在の構造が追跡を難しくしている場合に指摘する。

### 4. 変更シナリオで反証する

各機能について、今回の変更内容から現実的な将来変更を1〜3件だけ想定する。

例:

- 種別を一つ追加する
- 業務ルールの条件を一つ変更する
- 外部サービスを差し替える
- この機能を削除する
- 失敗時の扱いを変更する

その変更を行うと仮定し、次を確認する。

- どこを理解する必要があるか
- どこを変更する必要があるか
- 変更漏れをどう検出できるか
- 失敗したときどこを調査するか
- 不要になったときどこを削除するか

「改善できる」という理由だけでは指摘しない。現実的な変更シナリオで具体的なコストや誤変更の経路を説明できる場合だけ指摘する。

以下は、それ単独では指摘理由にしない。

- 関数が長い
- ネストが深い
- helperへ分割できる
- interfaceや抽象化を追加できる
- 有名な設計パターンを適用していない
- コードを短くできる
- コメントを追加できる

### 5. 最後に横断的な整合性だけ確認する

機能ごとの深掘りが終わった後で、必要な範囲に限って横断確認する。

- 同じ業務ルールが複数機能へ複製されていないか
- 同種の機能だけ構造、命名、失敗処理が不自然に異ならないか
- 共通概念の正本が分散していないか
- 変更理由に対して差分が過大になっていないか

横断確認から新しい探索を無制限に広げない。今回の変更に関係しない既存問題は、PRを止める指摘と分ける。

## 報告

指摘ごとに次を返す。

- 根拠となるファイルと行
- 該当する5観点
- 問題が表面化する具体的な変更・調査・障害対応シナリオ
- そのとき増える理解範囲、変更箇所、誤変更、検証、削除のコスト
- 問題より大きくならない最小の修正案

重大度は親 `review` が統一基準で決める。

問題がなければ、確認した機能と主な変更シナリオを簡潔に示して「問題なし」と返す。
