# 操作感の検証

## 守る結果

| 入力・状態 | 確認する結果 |
| --- | --- |
| 大きなwheel入力1回 | 隣の項目に止まり、中央に揃う。100だけでなく120、170、220、300pxなども試す |
| アニメーション中の連続入力 | 全入力が移動先へ加算され、2回分なら2項目先に着く。最後の入力後にも移動が続く |
| 正転・逆転 | 対称に移動し、予定位置が逆方向へ更新される |
| line/page単位のwheel | pixel用閾値と混同せず、隣の項目に移動する |
| 微小なpixel入力 | preventDefaultせず、ネイティブの連続入力を通す |
| Ctrl付きwheel・横方向優位 | ズームや横入力を奪わない |
| タッチのスワイプ | タッチイベント列で位置が動き、指を離した後に中央で確定する |
| 初期値・再読込・外部値変更 | 対象値が中央に戻る。確定通知がループしない |
| 候補変更・空・1件 | 古い移動先を使わず、空状態や端のボタンが破綻しない |
| キー・タップ・前後ボタン | 中央表示と確定値が一致し、ホイール移動中でも切り替えられる |
| reduced motion | キー等の移動に不要なアニメーションがない |
| 親状態・URL連動 | ページ位置を保ち、履歴や保存・通信をスクロール途中に増やさない |

## ブラウザでの確認

- Chromiumと、Safari向けならWebKitでも確認する。幅だけ変えたテストをタッチ操作の証明にしない。タッチエミュレーションとtouchStart/move/end等を使う。
- `page.mouse.wheel`は入力注入後すぐ戻るため、固定sleepではなく、確定値と中央位置を待つ。中央位置は選択行とスクロール領域のbounding boxの中心差で確認する（目安2px未満）。
- 滑らかさは最終値だけでは確認できない。連続入力直後の位置が到着位置より手前で、その後も位置が進むことを確認する。
- 入力補正だけを一時コピーやテストページで無効にし、大きな入力で隣の項目を飛ばすことを検出する。修正あり・なしで同じテストが通るなら、回帰テストの条件を見直す。
- イベントを合成した単体確認は単位変換・既定動作を奪わない分岐に使う。実際のスクロール確認にはブラウザのwheel/touch入力を使う。
- 実マウスの1目盛り、トラックパッドのフリック、iOS実機の慣性は自動入力と区別する。未実施の操作感を確認済みとしない。

## 今回の方式に至った失敗例

- 行高を64pxから88pxへ広げるだけでは、小さめの自動入力は改善しても実マウスの飛ばしが残った。
- 一定時間のwheel入力を捨てる方式は、続けて回したときの滑らかさを失った。
- `scroll-snap-stop: always`だけでは、試したwheel入力の飛ばしを防げなかった。
- 移動中に選択を親へ戻し、その値で再センタリングすると慣性を途中で止める。
- 大きな入力は隣までに補正し、未完了の移動先へ次の入力を積み足す方式で、元の利用者から操作感の評価を得た。他の端末でも同じ感触になる保証とはしない。
