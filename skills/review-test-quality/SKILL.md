# テスト品質レビュー

テスト数や分岐網羅だけでなく、各テストが必要な契約の破壊を検出できるかを確認する。

## 手順

1. 変更されたproduction code、呼び出し側、関連する仕様・ADR・portを読み、追加・変更・削除された契約、変更の影響を受ける維持すべき既存契約、失敗経路を列挙する。
2. 各契約について、破壊を検出する既存または変更テストを対応付ける。対応するテストがない場合は、追加不要と判断できる根拠があるか確認する。
3. 変更されたテストについて次を特定する。
   - 守る契約
   - 契約の根拠
   - 想定する回帰
   - 検証する境界
   - 観測可能な結果とAssert
4. いずれかを特定できない場合は、テスト名だけで補完せず、対象実装と利用箇所を調査する。
5. 指摘ごとにファイルと行、欠けている要素、起きうる誤検知または見逃し、修正案を返す。

## 確認観点

### 必要性と仕様根拠

- production codeだけが変更されている場合も、変更された契約と失敗経路に対応するテストの有無を確認する。
- 変更された各契約に、既存テストで十分、追加が必要、意図的に不要のいずれかを対応付けられる。
- 現在の仕様、domain rule、外部契約、port、再現した不具合のいずれかに根拠がある。
- 「標準的なパターンだから」「実装に分岐があるから」だけで新しい仕様を固定していない。
- 現在利用されない内部表現を、将来使うかもしれないという理由だけで固定していない。
- 回帰テストは、再発すると何が壊れるかを説明できる。

### テスト名と目的

- 名前または隣接する仕様記述から、対象、条件または操作、守る結果が読める。
- fault injectionやfixtureの作り方を、テスト目的として命名していない。
- `migrationを実行すると行が増える`のように、実装を言い直すだけになっていない。
- 名前が示す保証とAssertが一致する。

### 境界と観測方法

- `domain`、`usecase`、`adapter`などの語彙を形式的に要求せず、対象プロジェクトが実際に持つ境界へ対応付ける。
- 守る契約を所有する境界から検証している。
- 内部関数、中間値、SQLの形ではなく、利用側が観測する結果を優先している。
- migrationテストは、旧状態からのupgrade保証、既存データ保持、必要なら冪等性を検証している。
- E2Eへ細かな異常系を集めず、domain、usecase、adapter、APIの適切な境界へ置いている。

### Assertと失敗検出力

- 対象の実装を壊すと、意図した理由で失敗する。
- エラー値だけでなく、成功扱いしない、途中状態を残さない、外部詳細を漏らさないなど、目的に必要な結果を検証している。
- Arrangeが意図した障害や状態を確実に作っている。
- 一つのテストへ独立した複数の保証を詰め込んでいない。
- 他のテストと同じ保証を重複して固定していない。

## 重大度

親reviewを通じて使う場合は親の重大度基準に従う。単独で使う場合は次を目安にする。

- 重大: テストが誤った仕様を固定する、または重要な破壊を検出できない。
- 中: 仕様根拠、境界、Assertがずれ、将来の変更を妨げるか回帰を見逃す。
- 軽微: 目的は正しいが、名前、fixture、説明が読み取りにくい。

問題がなければ、確認した契約、根拠、境界を簡潔に示して「問題なし」と返す。
