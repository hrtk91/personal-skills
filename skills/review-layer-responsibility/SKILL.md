# レイヤー責務レビュー

## 目的

変更理由の異なる処理をレイヤーごとに分離し、一つの変更が無関係な箇所へ波及しない構造を保つ。

Clean Architectureの語彙は配置規則を機械的に強制するためではなく、各コードの役割を理解しやすくし、変更を担当する場所について共通認識を持つために用いる。まず対象プロジェクトが実際に採用している構造と規約を確認し、該当する役割を次の語彙へ対応付ける。

## レイヤーと境界

- adapter:
  外部システム、通信方式、永続化方式などとアプリケーションの間にあるインピーダンスミスマッチを吸収する外部接続層。driving adapterは外部入力を内側の呼び出しへ変換し、driven adapterは内側が要求する能力を外部技術で実現する。
- usecase:
  ユーザーや外部システムから見た一つの業務フローを記述する、domainの外殻側。domainのルールとportを介した外部能力を組み合わせ、処理の順序と成否を制御する。
- domain:
  業務上の概念、不変条件、判断、計算を記述するコア層。外部技術へ依存せず、可能な範囲で副作用のない関数として表現する。
- inbound port:
  アプリケーションが外側へ提供するユースケースの契約。usecase側が定義・実装し、driving adapterが呼び出す。
- outbound port:
  内側のレイヤーが外部へ求める能力の契約。その能力を必要とする最も内側のレイヤーが定義し、driven adapterが実装する。

## 永続化と読み取り

- Repository:
  集約をメモリ上のコレクションのように取得・保存するoutbound port。集約の概念としてdomain語彙に属する契約はdomain側へ置く。特定の業務フローだけが必要とする保存能力はusecase側のportとして分ける。
- Store:
  プロジェクトがRepository相当として定義している場合に、集約のload / saveへ責務を限定する名前として使える。名前だけでRepositoryと同じ責務だと判断しない。
- Query / Reads:
  特定の質問に必要な形で答えるoutbound port。読み取り専用ユースケースでは用途固有のapplication read modelを返し、表示書式や通信形式への整形はadapterへ置く。業務判断の材料を読む場合はdomain語彙の値や能力として契約し、画面用projectionと混ぜない。巨大な汎用Queryへ集約せず、利用目的ごとに必要な能力を分ける。
- 永続化実装 / ORM:
  テーブル、行、SQL、JOIN、ORMオブジェクト、commit / rollback APIなどを扱うadapter内の実装技術。RepositoryやQuery / Readsの契約と競合する概念ではない。

複数操作に原子性が必要な範囲はusecaseが決め、transaction runnerやUnit of Work相当のoutbound portを通じてadapterが実現する。一つのadapter実装が複数のportを実装してもよい。契約を分ける目的は実装クラスを増やすことではなく、利用側が必要とする能力を限定することである。

## レビュー手順

1. 変更差分、関連する呼び出し元、同種の既存実装、適用されるプロジェクト規約を読む。
   配置や共通化を判断する場合は、対象コードの利用箇所を先に検索し、一つの機能だけで使うか、複数の機能から使うかを確認する。
2. 今回の変更理由と、その変更を担当するレイヤーを特定する。
3. 次を確認する。
   - 業務ルールがadapterへ漏れ、外部接続先ごとに重複していない
   - 状態遷移によって成立した業務上の事実を、その状態遷移を成功させた業務操作が生成している。後続処理が完成済みの状態から事実を推測していない
   - usecaseは業務操作の順序と結果の受け渡しを調整し、adapterは業務上の事実を通信・保存の形式へ変換している。技術処理の成功を業務上の事実として扱っていない
   - 業務フローの順序、成否、原子性の範囲がadapterへ漏れていない
   - 外部技術、通信形式、永続化形式がusecaseやdomainへ漏れていない
   - Repositoryが任意条件の検索関数置き場になっていない
   - 読み取りだけのために不要な集約の復元を強制していない
   - Query / Readsが画面用projectionと業務判断の材料を混ぜていない
   - Query / Readsが何でも答える巨大な境界になっていない
   - portの契約を、その能力を必要とする最も内側のレイヤーが所有している
   - 一つの変更が、本来関係しないレイヤーへ波及していない
   - 一つの機能だけで使う処理を、将来使うかもしれないという理由だけで共通領域へ出していない
   - `support`や`common`など、何を担当するか分からない置き場所へ、分類に迷った処理を集めていない
4. 指摘では、変更理由、担当すべきレイヤー、責務が漏れている場所、将来の変更への影響を説明する。

守るべきルールや独立した変更理由がない単純な処理へ、形式だけのレイヤーやportを追加しない。境界はテスト用の差し替え箇所を増やすためではなく、責務と変更理由を分離する必要が生じた場所に設ける。ディレクトリ名は先に決めず、実際の利用範囲と変更理由を確認してから決める。

指摘ごとに根拠となるファイルと行、想定される影響、修正案を返す。重大度は親reviewが統一基準で決める。問題がなければ「問題なし」と返す。
