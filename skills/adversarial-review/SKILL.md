# 敵対的レビュー

変更が正しいと証明しようとせず、変更の主張を崩せる証拠を探す。通常の品質レビューを繰り返さず、「目的や前提が間違っている」「壊れていても検証を通る」可能性を優先する。

## 手順

### 1. 変更の目的を疑う

Issue、仕様、利用箇所、障害記録、変更前の挙動を原典で確認し、次を答える。

- 解こうとしている問題は実在するか。
- 利用者または呼び出し側が必要とする結果は何か。
- 原因ではなく症状だけを目的にしていないか。
- 変更しない選択肢や、より狭い境界で解決できないか。
- 目的を達成しても、別の重要な契約を損なわないか。

Issueや仕様に完了条件がある場合は、各条件と変更箇所を一対一で対応付ける。「使う技術を変えた」「設定を追加した」だけで、必要な結果が実現したと判定しない。

必須条件との矛盾を隠す回避策がないか確認する。たとえば、並列実行時の隔離が必要な変更を直列化し、競合が見えなくなっただけなら目的未達とする。

目的が誤っていれば、実装の細部より先に指摘する。

### 2. 変更の主張を列挙する

PR本文や実装から、変更が成立するための主張を検証可能な文にする。

例:

- 不正な入力は永続化前に拒否される。
- 同じ操作を再試行しても結果が重複しない。
- 対象処理を壊すと回帰テストが失敗する。

曖昧な説明をそのまま前提にしない。対象、条件、観測できる結果を補う。

### 3. 各主張を崩す

差分だけでなく、入口、利用箇所、永続状態、外部境界、テストfixtureを追う。変更に関係するものを優先し、次の攻撃を試す。

- 前提欠落: 未設定、空、境界値、古いデータ、想定外の順序でも成立するか。
- 抜け道: 別の入口、別形式、権限違い、再試行から同じ制約を回避できないか。
- 部分失敗: 外部I/Oや保存の途中で失敗したとき、成功扱いや中間状態を残さないか。
- 後始末: 変更箇所だけで判断せず、resourceを最終的に所有する処理や実行単位まで追い、本来の生存期間が終わる時点で解放されるか確認する。変更箇所では解放されなくても適切な時点で解放される場合と、生存期間を過ぎても残る漏れを区別する。処理を繰り返したときに解放前のresourceが蓄積し、上限へ達しないかも確認する。
- 状態依存: 単独では通るが、順番変更、二回実行、並列実行、共有fixtureで壊れないか。
- 誤検知: 正常な入力や既存利用者まで拒否しないか。
- 偽の安心: 対象が壊れている、fixtureが空、mockが都合よく動く場合でもテストが通らないか。
- 契約ずれ: 呼び出し側、文書、設定、migration、監視が古い前提を持っていないか。
- 情報隠蔽: エラーの握りつぶし、既定値、空配列、ログだけの失敗で異常を隠していないか。

チェック項目を機械的に消化せず、その変更を最も壊しやすい仮説から調べる。

調査は変更の目的、変更された主張、直接影響する契約へ限定する。既存問題はPRを止める指摘と分ける。通常は可能性と影響が高い仮説を最大5件まで深掘りし、根拠の薄い網羅探索へ広げない。

### 4. 反証実験を行う

反証実験は、ユーザーが一時的なコード変更を明示的に許可した場合だけ行う。レビュー依頼だけを変更の許可とみなさない。変更の中心処理を無効化または逆転させ、守るはずのテストが失敗するか確認する。テストが成功したままなら、回帰テストは変更の主張を守れていない。

実験時は専用worktreeを使い、開始前がcleanであることを確認する。逆パッチを先に用意し、テストの成否にかかわらず直後に復元し、開始前後のdiffが一致することを確認する。ユーザーの変更を失うおそれがある操作、本番状態の変更、復元を保証できない実験は行わない。その場合は静的な反証手順だけを示す。

### 5. 敵対的レビュー結果を敵対的に再検証する

見つけた指摘を正しいと仮定せず、一件ずつ反証する。

- 成立条件は本番または現実的な運用で起こりうるか。
- 根拠は実装、仕様、実行結果にあり、単なる可能性の列挙ではないか。
- 既存の別レイヤー、DB制約、外部サービスがすでに防いでいないか。
- 変更前から存在する問題を、この変更の回帰として誤認していないか。
- テスト境界に求めていない責務まで要求していないか。
- 重大度を利用者影響より大きく見積もっていないか。
- 指摘した問題が、本来の生存期間が終わる時点の終了処理でも解消されず、その後も残ることを確認したか。
- 提案する修正が問題より大きく、別の不具合を増やさないか。

反証できた指摘は削除する。確証が足りないものは、具体的な根拠と一つの確認方法がある場合だけ「要確認」とする。「要確認」は最大3件とし、それ以外の未確認事項を網羅的に列挙しない。残った指摘について、反証に使った証拠も報告する。

可能なら一次レビューとは別のreviewerへ、一次指摘と対象の原典だけを渡して反証させる。一次reviewerの結論や期待する判定を補強する説明は渡さない。自己反証は一回で終了し、二次reviewerは同じskillによる追加委譲や三次レビューを行わない。

### 6. 通常条件と分離して報告する

指摘は次を含める。

- 重大度
- 崩れた主張または疑わしい目的
- 根拠となるファイルと行
- 成立させる入力、状態、実行順
- 利用者または呼び出し側に起きる結果
- 最小の修正または追加検証

正式な指摘は影響の大きい順に最大5件とする。問題が見つからない場合も、試した主な攻撃、反証できなかった主張、残る未検証領域をそれぞれ最大3件まで報告する。「問題なし」だけで終えない。

## 重大度

- 重大: 現実的に発生しうる条件で、目的が成立しない、主要契約を満たさない、またはセキュリティ・データ破壊・課金誤りにつながり、容易に回復できない。
- 中: 現実的な入力や状態で回避・誤動作できる、またはテストが重要な回帰を検出できないが、影響が限定的または回復可能である。
- 軽微: 現在の挙動は守れるが、説明や診断性の不足で将来の誤変更を誘発する。
