# 設計レビュー

実装できるかではなく、元の目的を満たし、将来の変更を受け止められる設計かを実装前に判断する。

## 0. 壊れ方から保証と設計を導く

設計とは、何が壊れうるかを洗い出し、どの壊れ方まで防ぎ、どこから先を許容するかを決めること。`Outbox`、retry、idempotency、state machineなどの手段を、一般に良い設計として先に選ばない。

まず成功フローを境界ごとに分け、各境界で起こりうる失敗を列挙する。

```text
入力保存 → 非同期処理要求 → 外部サービス処理 → 利用枠消費 → 結果保存
```

例として、入力保存後のプロセス終了、イベントの重複配送、外部サービスのタイムアウトや長時間停止、利用枠だけ消費されて処理に失敗する部分失敗、再処理による二重課金を挙げる。

次に、各リスクについて次を短く決める。

- 起きやすさ、起きたときの被害、対応コストを見積もる
- `防ぐ`、`軽減する`、`受け入れる`のいずれかを選ぶ
- 選んだ方針から、必要な保証と対象外（許容する壊れ方）を明記する

設計判断は、次の順序で記録する。

```text
リスク → 要求する保証 → 制約・コスト → 設計判断 → 検証方法
```

たとえば、入力から処理要求が消えることを防ぐなら`Outbox`、重複配送を前提にするなら冪等化、一時的な外部サービス障害なら上限付きretryを候補にする。ただし、数日間のサービス停止やリージョン全損時のRPO 0まで自動復旧するかは、要求する保証と対応コストを比較して対象外にもできる。仕組みの採用理由を、必ず元のリスクと保証へ戻って説明する。

変更容易性も未来の変更をリスクとして扱う。「料金体系が変わる」「LLMを差し替える」「別の決済手段が増える」など、起こりそうで起きたときに高くつく変化だけ境界を設ける。あらゆる未来を予言するために抽象化を増やさない。

## 1. 原典から設計条件を復元する

Issue、仕様、ADR、利用箇所、現行実装、障害記録などの原典を読み、次を分ける。設計案やPR本文の説明だけで補わない。

- 目的: 誰または何に、どんな結果が必要か
- 必須条件: 満たさなければ完了と言えない条件
- 手段: 目的を達成するための変更可能な選択
- 対象外: 今回は解かない問題
- 未確定: 設計を選ぶ前に調査または判断が必要な点

必須条件を回避する案を、単純さや実装コストの低さだけで採用しない。たとえば、並列実行時の隔離が必須なら、直列化で競合を隠す案は条件未達とする。

## 2. 独立subagentにレビューさせる

原則として`architect` subagentを1つ起動する。`architect`が使えない場合は、設計判断が可能な高推論のsubagentを使う。subagentを利用できない場合だけmain agentが同じ手順でレビューし、その制約を報告する。

subagentは会話履歴を継承しないfresh contextで起動し、次の情報だけを渡す。利用基盤が履歴を分離できない場合は、独立性の制約をレビュー結果に明記する。

subagentへ渡すもの:

- ユーザーの依頼文
- Issue、仕様、ADRなどの原典パスまたは本文
- 設計案と代替案
- 確認済みの現行実装と制約
- この`SKILL.md`のパスと、最初に全文読む指示
- 調査対象のファイル、機能、またはIssueの範囲と、指定形式の判定を返したら終了する条件
- 「あなたが指定されたreviewerである。このskillのsection 2にあるsubagent起動は実行せず、section 1・3・4を実行する」という指示

subagentへ渡さないもの:

- main agentが期待する結論
- 設計案を採用させるための説得
- 根拠未確認の解釈

subagentには読み取りと設計レビューのみを依頼し、コード変更やさらなるsubagentへの委譲を許可しない。
調査は必須条件、設計案が変更する境界、直接関係する現行実装へ限定する。リポジトリ全体の品質問題へ広げず、判定に必要な根拠が揃ったら追加探索を終える。

## 3. 設計の成立条件を確かめる

subagentは設計案ごとに次を確認する。対象に関係する項目を優先し、用語やパターの形式的な適用にしない。

### 目的と条件

- 各必須条件をどの仕組みが満たすか
- 手段を導入すること自体が目的化していないか
- 条件を満たさず、問題を見えなくするだけの回避策がないか

### リスクと保証

- 各重要リスクに、要求する保証と対応方針（防ぐ / 軽減する / 受け入れる）が対応しているか
- 受け入れたリスクに、対象範囲、検知方法、必要なら復旧手段があるか
- 選んだ仕組みが、必要な保証を超える複雑さやコストを持ち込んでいないか

### 責務と変更容易性

- 変更理由の異なる処理が一つの場所へ集まっていないか
- 今後変わりやすい部分が、無関係な利用箇所へ波及しないか
- 抽象化が実際の変更理由を分けているか
- 新しい概念や境界が問題に対して過大でないか

### resourceとライフサイクル

外部resource、DB、transaction、process、thread、Actor、connection、lockを扱う場合は、resourceごとに次を確定する。

- 所有者
- 生存期間と共有範囲
- 取得と正常終了時の解放
- 後続resourceの取得失敗時に、先行resourceを解放する経路
- 所有者の異常終了時の回収
- 解放失敗時の再試行または検知

複数resourceを順番に取得する場合は、各段階で次の取得が失敗する条件を列挙する。

### 並列性と隔離

- 共有状態と競合する操作は何か
- 正しさを保つ隔離方式は何か
- 同時実行数の上限と、正しさを守る仕組みを混同していないか
- 競合を起こすデータや同期点を使い、並列性と非干渉を直接検証できるか

### 技術的な前提

- framework、library、runtimeの実行モデルを公式資料または最小実験で確認したか
- 外部サービスと統合する場合は、公式SDK、公式資料で案内されるlibrary、保守状況を確認できる既存実装の順に調べたか
- 独自実装を選ぶ場合は、既存の選択肢で満たせない契約と、自分たちが所有することになる型、通信、再試行、cleanupなどの責務を説明できるか
- 現行実装と履歴を確認し、概念を「既存」「今回変更」「今回新規」に分けたか
- 未確認の技術前提を根拠に設計を固定していないか

### 検証可能性

- 各必須条件をどの境界から確認できるか
- 仕組みの存在ではなく、必要な性質を直接検証できるか
- 中心の仕組みを壊したとき、検証が失敗するか
- 失敗時に成功扱い、中間状態の残留、resource漏れを検出できるか

## 4. 設計案を判定する

subagentは次の形式で返す。

```text
## 設計レビュー

判定: 採用 / 要修正 / 棄却

目的と必須条件:
- 条件: 根拠 -> 設計の対応箇所 -> 充足 / 未充足 / 未確認

リスクと保証:
- リスク: 起きやすさ・被害 -> 要求する保証 -> 防ぐ / 軽減する / 受け入れる -> 設計・検証 -> 対象外

重要指摘:
- [重大 / 中 / 軽微] 崩れる条件、根拠、影響、最小の修正

resourceと失敗経路:
- resource: 所有者 / 生存期間 / 正常解放 / 部分失敗 / 異常終了

未確定事項:
- 設計決定前に確認する事実と確認方法

推奨案:
- 目的を満たす最小の設計とトレードオフ
```

判定基準:

- 採用: 必須条件を満たし、重大・中の設計問題がない
- 要修正: 目的は妥当だが、修正すべき未充足条件または失敗経路がある
- 棄却: 必須条件と矛盾する、またはより狭く単純な設計で目的を満たせる

## 4.5 採用結果を実装可能な契約へ変換する

採用判断で「実装へ進む」を返す場合、設計審査の結果は次の構造へ変換して渡す。

1. 目的・必須条件: 設計が満たす条件を、1行ずつ確認可能な形にする
2. 境界と責務: 変更理由の異なる処理を誰が担当するかを書く
3. 失敗経路: 事前条件違反、部分失敗、回復不能失敗を分ける
4. 不変条件: 業務上守る条件と、その確認方法を列挙する
5. handoff情報: 実装担当が最初に見る箇所、採用しない方法、受入QCを明記する
6. 受け入れたリスク: 対象外にした壊れ方、理由、検知・復旧の要否を明記する

詳細なhandoff設計は`orchestrate-exploration/SKILL.md`の「実装を渡す契約」参照。不足がある場合は「要修正」に戻す。

判定は以下を同時に返すこと。

- 採用 / 要修正 / 棄却
- 確認済みエビデンス
- 未充足・未確認条件

## 5. main agentが最終判断する

main agentはsubagentの結論をそのまま採用しない。原典と現行実装を確認し、次を行う。

1. subagentが挙げた必須条件と原典を照合する。
2. 指摘の成立条件が現実的か確認する。
3. 修正案が問題より過大でないか確認する。
4. 必須条件と設計案の対応、判定、未確定事項をユーザーへ報告する。

判定が「要修正」または「棄却」の場合は、設計を更新してから実装する。未確定事項が設計を分岐させる場合は、調査またはユーザーの判断を先に行う。
