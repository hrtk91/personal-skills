# 設計レビュー

実装できるかではなく、元の目的を満たし、将来の変更を受け止められる設計かを実装前に判断する。
レビューのフローを回す際に発生した懸念や未確定事項はその重要度を見積もり、最終成果出力前に重要度の低いものは切り捨てること。
レビューすることと同様かそれ以上に集中すべき課題を見極めることが重要。

## 0. 原典から設計条件を復元する

Issue、仕様、ADR、利用箇所、現行実装、障害記録などの原典を読み、次を分ける。設計案やPR本文の説明だけで補わない。

- 目的: 誰または何に、どんな結果が必要か
- 完了条件: 満たさなければ完了と言えない条件
- 手段: 目的を達成するための変更可能な選択
- 対象外: 今回は解かない問題k
- 未確定: 設計を選ぶ前に調査または判断が必要な点

**注意事項**
- このとき、完了条件、異なる利用者価値、異なる変更境界、または独立した受け入れ単位に分かれる場合は、タスク分割によって設計を単純化できないか検討する。
- 完了条件を回避する案を、単純さや実装コストの低さだけで採用しない。たとえば、並列実行時の隔離が必須なら、直列化で競合を隠す案は条件未達とする。

## 1. 壊れ方から保証と設計を導く

設計とは、何がどのように壊れうるかを洗い出し、どこまでを守り、どこからを許容するかを決めること。

まず成功フローの境界に着目し、各境界で起こりうる失敗を列挙する。
例として、入力保存後のプロセス終了、イベントの重複配送、外部サービスのタイムアウトや長時間停止、利用枠だけ消費されて処理に失敗する部分失敗、再処理による二重課金を挙げる。

次に、各リスクについて次を短く決める。

- 起きやすさ、起きたときの被害、対応コストを見積もる
- `防ぐ`、`軽減する`、`受け入れる`のいずれかを選ぶ
- 選んだ方針から、必要な保証と対象外（許容する壊れ方）を明記する

設計判断は、次の順序で記録する。

```text
リスク → 要求する保証 → 制約・コスト → 設計判断 → 検証方法
```

たとえば、入力から処理要求が消えることを防ぐなら`Outbox`、重複配送を前提にするなら冪等化、一時的な外部サービス障害なら上限付きretryを候補にする。ただし、数日間のサービス停止やリージョン全損時のRPO 0まで自動復旧するかは、要求する保証と対応コストを比較して対象外にもできる。仕組みの採用理由を、必ず元のリスクと保証へ戻って説明する。

変更容易性も未来の変更をリスクとして扱う。「料金体系が変わる」「外部サービスを差し替える」「別の決済手段が増える」など、起こりそうで起きたときに高くつく変化だけ境界を設ける。あらゆる未来を予言するために抽象化を増やさない。


## 2. 独立subagentにレビューさせる

原則として設計判断が可能な高推論のsubagentを召喚する。subagentを利用できない場合だけmain agentが同じ手順でレビューし、その制約を報告する。

subagentは会話履歴を継承しないfresh contextで起動し、次の情報だけを渡す。利用基盤が履歴を分離できない場合は、独立性の制約をレビュー結果に明記する。

subagentへ渡すもの:

- ユーザーの依頼文
- Issue、仕様、ADRなどの原典パスまたは本文
- 設計案と代替案
- 確認済みの現行実装と制約
- この`SKILL.md`のパスと、最初に全文読む指示
- 調査対象のファイル、機能、またはIssueの範囲と、指定形式の判定を返したら終了する条件
- 「あなたが指定されたreviewerである。このskillのsection 2にあるsubagent起動は実行せず、section 1・3・4を実行する」という指示

subagentへ渡さないもの:

- main agentが期待する結論
- 設計案を採用させるための説得
- 根拠未確認の解釈

subagentには読み取りと設計レビューのみを依頼し、コード変更やさらなるsubagentへの委譲を許可しない。
調査は完了条件、設計案が変更する境界、直接関係する現行実装へ限定する。リポジトリ全体の品質問題へ広げず、判定に必要な根拠が揃ったら追加探索を終える。

## 3. 設計の成立条件を確かめる

subagentは設計案ごとに次を確認する。対象に直接関係する項目を優先し、用語やパターンを形式的に当てはめない。

### 目的と条件

- 各完了条件を満たす設計が行われているか
- 手段を導入すること自体が目的化していないか
- 条件を満たさず、問題を見えなくするだけの回避策（ハック）になってないか

### リスクと保証

- リスクの見積は発生頻度と発生した際の影響について、過剰評価でも過小評価でもないか
- 各重要リスクに、要求する保証と対応方針（防ぐ / 軽減する / 受け入れる）が対応しているか
- 受け入れたリスクに、対象範囲、検知方法、必要なら復旧手段があるか
- 選んだ仕組みが、必要な保証を超える複雑さやコストを持ち込んでいないか

### 責務と変更容易性

- 異なる理由で独立に変わる処理を、不必要に同じ境界へ結び付けていないか
- 今回想定する変更が、関係する範囲だけで完結するか
- 既存コードを変更すること自体を欠点として扱っていないか
- 変更を避けるためだけに、抽象化や拡張点を増やしていないか
- 新しい概念や境界が、実際の変更頻度と変更コストに見合っているか

### リソースとライフサイクル

外部リソース、DB、transaction、process、thread、Actor、connection、lockを扱う場合は、リソースごとに次を確認する。

- 所有者
- 生存期間と共有範囲
- 取得と正常終了時の解放
- 後続リソースの取得失敗時に、先行リソースを解放する経路
- 所有者の異常終了時の回収
- 解放失敗時の再試行または検知

複数リソースを順番に取得する場合は、各段階で次の取得が失敗する条件を列挙する。

### 並列性と隔離

- 共有状態と競合する操作は何か
- 正しさを保つ隔離方式は何か
- 同時実行数の上限と、正しさを守る仕組みを混同していないか
- 競合を起こすデータや同期点を使い、並列性と非干渉を直接検証できるか

### 技術的な前提

- framework、library、runtimeの実行モデルを公式資料または最小実験で確認したか
- 外部サービスと統合する場合は、公式SDK、公式資料で案内されるlibrary、保守状況を確認できる既存実装の順に調べたか
- 独自実装を選ぶ場合は、既存の選択肢で満たせない契約と、自分たちが所有することになる型、通信、再試行、cleanupなどの責務を説明できるか
- 現行実装と履歴を確認し、概念を「既存」「今回変更」「今回新規」に分けたか
- 未確認の技術前提を根拠に設計を固定していないか

### 検証可能性

- 各完了条件をどの境界からテストすることで確認できるか
- 実現するための仕組みの検証になっていないか（抽象化レイヤーの存在有無を確認するテストになってないか）
- 目的達成に必要な性質を検証できるか
- テスト失敗時の成功扱い（偽陰性）、中間状態の残留、リソース漏れを検出できるか

## 4. 設計案を判定する

subagentは次の形式で返す。

```text
## 設計レビュー

判定: 採用 / 要修正 / 棄却

目的と完了条件:
- 条件: 根拠 -> 設計の対応箇所 -> 充足 / 未充足 / 未確認

リスクと保証:
- リスク: 起きやすさ・被害 -> 要求する保証 -> 防ぐ / 軽減する / 受け入れる -> 設計・検証 -> 対象外

重要指摘:
- [重大 / 中 / 軽微] 崩れる条件、根拠、影響、最小の修正

リソースと失敗経路:
- リソース: 所有者 / 生存期間 / 正常解放 / 部分失敗 / 異常終了

未確定事項:
- 設計決定前に確認する事実と確認方法

推奨案:
- 目的を満たす最小の設計とトレードオフ
```

判定基準:

- 採用: 完了条件を満たし、重大・中の設計問題がない
- 要修正: 目的は妥当だが、修正すべき未充足条件または失敗経路がある
- 棄却: 完了条件と矛盾する、またはより狭く単純な設計で目的を満たせる

## 4.5 採用結果を実装可能な契約へ変換する

採用判断で「実装へ進む」を返す場合、設計審査の結果は次の構造へ変換して渡す。

1. 目的・完了条件: 設計が満たす条件を、1行ずつ確認可能な形にする
2. 境界と責務: 変更理由の異なる処理を誰が担当するかを書く
3. 失敗経路: 事前条件違反、部分失敗、回復不能失敗を分ける
4. 不変条件: 業務上守る条件と、その確認方法を列挙する
5. handoff情報: 実装担当が最初に見る箇所、採用しない方法、受入QCを明記する
6. 受け入れたリスク: 対象外にした壊れ方、理由、検知・復旧の要否を明記する

判定は以下を同時に返すこと。

- 採用 / 要修正 / 棄却
- 確認済みエビデンス
- 未充足・未確認条件

## 5. main agentが最終判断する

main agentはsubagentの結論をそのまま採用しない。原典と現行実装を確認し、次を行う。

1. subagentが挙げた完了条件と原典を照合する。
2. 指摘の成立条件が現実的か確認する。
3. 修正案が問題より過大でないか確認する。
4. 発生した懸念や未確定事項はその重要度を見積もり、最終成果出力前に重要度の低いものは切り捨てる。
5. 完了条件と設計案の対応、判定、未確定事項をユーザーへ報告する。

判定が「要修正」または「棄却」の場合は、設計を更新してから実装する。未確定事項が設計を分岐させる場合は、調査またはユーザーの判断を先に行う。
