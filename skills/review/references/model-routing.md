# review モデルルーティング

特定のモデル名を固定せず、実行時に利用可能なモデルからタスク難易度に合うものを選ぶ。agent名やモデル名の印象だけで能力を推測しない。現在のセッションが提示するagent/model metadata、Codexのモデルカタログ、または公式の現行モデル説明を情報源にし、agent設定とspawn時の指定で実効モデルと推論レベルを確認する。

## 難易度を判定する

### 定型レビュー

探索手順と期待する契約が明確で、検索と根拠収集を中心に閉じられる観点へ使う。

- 命名一貫性
- 型と利用箇所の追跡
- 影響範囲
- 保守性
- 仕様と契約が明確なテスト品質
- 境界が限定されたレイヤー責務
- 高リスク領域を含まない変更での入力検証、出力エスケープ、パス、ログ漏えいなど定型的なセキュリティ確認

現在のモデルカタログまたは公式説明で、安価・高速かつ明確で反復的または高量なタスク向けと確認できるモデルを選ぶ。そのモデルが対応する最大の推論レベルを使い、安価なモデルへ十分な探索と反証を行わせる。最大レベルが `max` とは限らないため、実際のsupported reasoning levelsを確認する。大量のrenameや機械的変更は、差分が大きくても高能力モデルへ切り替える理由にしない。

read-onlyの定型レビュー用roleが利用可能なら第一候補にする。現在の設定では`routine-reviewer`がこの役割を担う。名前だけで判断せず、実効モデルが現在も安価・高速な定型タスク向けであること、十分な推論レベルであること、sandboxがread-onlyであることを確認する。実装用のwrite可能なroleへレビューを依頼しない。

注入済みのspawn候補だけで最安モデルを判断しない。候補一覧が不完全な場合があるため、利用可能なら現在のCodex model catalogも確認する。安価・高速モデルを特定できない場合は、利用可能な効率重視モデルを選び、その選択が暫定であることを報告する。

### deep review

次のいずれかを含む観点へ最初から使う。

- 目的、仕様、期待する契約が曖昧
- 複数レイヤーをまたぐ設計変更
- 認証、認可、課金、個人情報
- migration、永続化形式、既存データ変換
- 並行処理、排他制御、再試行、冪等性
- データ破壊や外部公開操作
- 公開API、設定形式、外部連携契約
- コード検索だけでは影響範囲を閉じられない変更
- 暗黙の前提を疑う敵対的レビュー

deep reviewerには、利用可能なモデルのうち、現在のmetadataまたは公式説明で曖昧かつ複数段階の推論、計画、検証を伴うタスク向けと確認できるモデルを選ぶ。推論レベルは最低 `high` とし、複数の危険要素が重なる場合や前提自体を疑う場合は `xhigh`、`max`など利用可能な上位レベルへ上げる。モデル能力を現在の情報源から確認できない場合は、推論レベルだけを上げてdeep reviewの条件を満たしたことにしない。

## 事後昇格

定型レビューの結果が次に該当したら、候補をまとめてdeep reviewerに反証させる。

- 重大度にかかわらず、成立条件や責務の判断に不確実性がある
- 問題なしだが未確認領域が残る
- 仕様、ADR、利用箇所などの根拠を特定できない
- reviewer間で結論が矛盾する
- 可能性は示したが現実の成立経路を証明できない
- 高リスク領域で問題が見つからず、独立した反証が必要

deep reviewerは各候補について、成立経路、別レイヤーやDB制約の防御、変更前からの問題か、重大度、修正案の過大さを原典から確認する。候補ごとにagentを増やさず、独立性を損なわない範囲で一度の反証依頼へまとめる。

## 選択できない場合

希望するモデルまたは推論レベルを指定できない場合もレビュー自体は止めない。利用可能なread-only agentまたは親agentへフォールバックする。ただし、高リスク領域を能力未確認のモデル、低能力モデル、または `medium` 以下の推論だけで最終判定しない。条件を満たすreviewerを用意できなければ、その領域を未検証として報告する。

最終報告には、観点ごとに実際に利用したagent、モデル、推論レベル、選択理由、昇格、未検証領域を簡潔に残す。モデルや推論レベルを確認できない場合は推測せず「不明」と書く。
