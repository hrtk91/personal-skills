# review スキル

変更差分を、7つの観点でレビューして報告する。

目的は変更の欠陥・責務逸脱・影響範囲の追従漏れ・テスト不足を見つけること。小さな差分ではメインエージェントだけで簡易レビューする。中〜大規模の差分では、観点の曖昧さ・危険度・複合性に応じてreviewerのモデルと推論レベルを選び、必要な結果だけdeep reviewへ昇格させる。

## 手順

### 1. 変更ファイルの特定

- 指定がなければbase branchとの差分で変更ファイル一覧を取得する。
- base branchは `main` とは限らない。必要なら `git merge-base` やリモートdefault branchを確認する。
- commit済み、staged、unstaged、untrackedの変更をすべて統合する。`git diff --name-only`、`git diff --name-only --cached`、`git ls-files --others --exclude-standard`を確認する。
- 変更ファイルだけでなく、呼び出し元・型定義・ルーター・設定・テストも必要に応じて読む。

### 2. レビュー観点

このreviewは、次の6つの兄弟skillと一組で利用するmeta-skillである。参照先が存在しない場合はレビューを開始せず、不足しているskillを報告する。

- `review-naming`
- `review-layer-responsibility`
- `review-type-safety`
- `review-maintainability`
- `review-impact-analysis`
- `review-test-quality`

#### 命名一貫性

`../review-naming/SKILL.md`を全文読み、その手順に従う。

#### レイヤー責務 / 依存方向

`../review-layer-responsibility/SKILL.md`を全文読み、その手順に従う。

#### 型安全性

`../review-type-safety/SKILL.md`を全文読み、その手順に従う。

#### セキュリティ

確認すること:

- 認証(Authentication)と認可(Authorization)の責務が混ざっていないか。
- 権限判定など現在状態を確認すべきルールを、古いスナップショット情報だけで判断していないか。
- 権限チェックが画面やクライアント側表示だけに閉じておらず、サーバ側や信頼できる境界で実施されているか。
- 入力検証、出力エスケープ、パス/クエリ/ヘッダ/ファイル名の扱いに注入や改ざんの余地がないか。
- secret、token、個人情報、内部情報がログ、エラー、レスポンス、リポジトリに漏れないか。
- 破壊的操作や外部公開操作に確認、dry-run、権限分離などの安全策があるか。

#### 保守性

`../review-maintainability/SKILL.md`を全文読み、その手順に従う。

#### 影響範囲

`../review-impact-analysis/SKILL.md`を全文読み、その手順に従う。

#### テスト充足性

`../review-test-quality/SKILL.md`を全文読み、その手順に従う。テストの不足だけでなく、追加されたテストが仕様根拠のない実装詳細を固定していないかも確認する。

### 3. 実行スタイル

- 小さな差分: メインエージェントが7観点をまとめて簡潔に見る。
- 中〜大きい差分: `references/model-routing.md`を全文読み、観点ごとにタスク難易度、モデル能力、推論レベルを選ぶ。
- 独立skillがある観点では、対応するskillを最初に全文読ませる。
- 定型レビューをsubagentへ委譲する場合は、read-onlyの定型レビュー用roleを優先する。現在の設定では`routine-reviewer`がこの役割を担う。利用できない場合は、read-onlyを保証できるagentかメインエージェントへ戻す。書き込み可能な実装用roleへ編集禁止と伝えるだけで代用しない。小さな差分をメインエージェントだけで確認する場合はモデルを切り替えない。
- 高リスク領域は最初からdeep reviewerへ割り当てる。deep reviewerには利用可能な高能力モデルと `high` 以上の推論レベルを使う。差分行数だけを理由に昇格しない。
- 定型レビューの結果が事後昇格条件に該当する場合、候補をまとめてdeep reviewerに反証させる。
- 複数サブエージェントを使う場合でも、最終判断はメインエージェントが原典を確認して行う。
- 希望するモデルまたは推論レベルを指定できない場合は、利用可能なread-only agentまたはメインエージェントへフォールバックし、実際の構成と未検証領域を報告する。
- 指摘は重大度順に並べる。

#### reviewer subagentを正常終了させる

- 依頼時に対象ファイル、実行する検証、報告形式、終了条件、最初のcheckpoint、期待する進捗信号を明示し、探索範囲を広げすぎない。read-onlyレビューで途中成果物を残さない場合は、正常な無報告時間と状況確認を始める時点を決める。
- `wait` のタイムアウトは失敗や停止を意味しない。短いwaitを繰り返したり、応答がないという理由だけでrunning中のagentをcloseしない。
- 通常は60〜120秒単位で完了を待つ。この間隔は監視間隔であり、停止期限ではない。statusがrunningのままでも、メッセージや成果物に進捗があれば待機を続ける。
- 予定したcheckpointを越えて2回連続でメッセージと成果物の両方に進捗がない場合だけ、状況確認を一度送る。さらに1監視間隔進捗がなく、調査の打ち切りが必要な場合は、interruptで「探索を打ち切り、確認済みの高確度な指摘だけを最終回答として返し、正常終了する」と明示する。
- interrupt後は再度waitし、`completed`と最終回答を受け取ってからagentをcloseする。正常終了できなかった場合は、実行したwait、interrupt、最終statusを報告し、メインエージェントが原典を確認してレビューを完了する。

重大度:

- 重大: マージすると仕様破壊、セキュリティ問題、自動テスト失敗、データ破壊が起きうる。
- 中: 今すぐ壊れないが、責務逸脱、追従漏れ、テスト不足、将来のバグ温床になる。
- 軽微: 命名、コメント、読みやすさ、追加テストの改善提案。

### 4. 報告形式

指摘がある場合:

```text
## レビュー結果

- [重大] path:line — 内容
- [中] path:line — 内容
- [軽微] path:line — 内容

補足:
- 問題なしだった観点や、確認したが採用しなかった懸念を書く。

レビュー構成:
- 観点: 利用したagent、モデル、推論レベル（選択理由）

昇格・フォールバック:
- 理由と実際に利用したagentを書く。該当なしなら省略する。

未検証領域:
- 原典から閉じられなかった領域を書く。該当なしなら「なし」と書く。
```

指摘がない場合:

```text
全観点で問題なし。

確認した観点:
- 命名一貫性
- レイヤー責務 / 依存方向
- 型安全性
- セキュリティ
- 保守性
- 影響範囲
- テスト充足性

レビュー構成:
- 観点: 利用したagent、モデル、推論レベル（選択理由）

未検証領域:
- なし
```
