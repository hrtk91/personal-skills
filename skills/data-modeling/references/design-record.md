# 設計記録の項目

対象のデータの持ち方を記録するときに使う。既存資料があれば該当部分を更新し、同じ説明を別文書へ複製しない。以下は記載内容の目安であり、見出しや表の形は既存資料に合わせる。

## 利用例とデータの関係

誰が何をするためのデータかを具体例で説明する。関係を示すER図では、変更前と変更後を区別し、一対多などの関係と所属先が分かるようにする。保存形式がJSONでも、中に含むデータの関係を隠さない。

## 各項目の説明

対象範囲について、次を記す。分からない値を埋めず、未確認と確認先を書く。

| 項目 | 書く内容 |
| --- | --- |
| 意味と利用例 | 何のためにあり、どの操作で使うか。値の具体例 |
| 型と単位 | SQL型だけでなく、分・秒などの単位、許される値や範囲 |
| 値がない場合 | NULL、空文字、空配列がそれぞれ何を意味するか |
| JSONの中身 | 具体的な型、必須項目、配列要素の意味、順序の意味 |
| 検証とDB制約 | 不正な値をどこで拒否するか。重複や参照先の存在をどう保証するか |

## 前提を残す場所

項目の意味・単位・NULLの意味・誤用しやすい前提は、DBコメントまたは管理元のスキーマ定義に残す。DBコメントを使えない環境では、スキーマ近くの説明から参照できるようにする。稼働DBへ直接コメントを加えるだけで済ませず、変更を再現できる管理方法に従う。

複数の項目や操作にまたがる理由、比較した案、見直し条件は設計資料へ置く。コメントと資料は参照でつなぎ、同じ長文を複製しない。仕様変更時は該当する説明も更新する。

## あとから説明するための記録

監査が必要な場合、答える必要のある問いと、編集・アクセス・課金などの出来事を対応させる。主体、対象、時刻、結果、必要な変更前後の値、操作と再試行を結ぶ識別子を定める。何でも保存するのではなく、必要性から項目を選ぶ。

業務データの削除後にも残す情報、記録失敗時の動作、重複や欠落への対策、閲覧・変更権限、保存期間を書く。外部処理の結果が不明な場合は、成功扱いせず、照合と復旧の方法を示す。監査記録を置くことだけで、二重実行や改変を防げるとは説明しない。

## 保存する操作

操作ごとに、操作できる人、読むデータ、変えるデータ、まとめて成功・失敗させる範囲を書く。同時操作や古い画面からの更新をどう扱うかも示す。保証している実装箇所と、これから実装する案を区別する。

## 選んだ理由と次に見直す条件

維持・説明の補足・構造変更の判断と、その根拠を書く。JSONで持つ、別テーブルへ分けるなどの選択は、具体的な使い方から説明する。簡略化を残すなら、省いたことと再検討する変化を書く。

## 変更前後と確認方法

変更する場合に記す。各データの移行先、変換できない値の扱い、切り替え中の読み書き、失敗時の復旧を必要な範囲で説明する。確認したい結果と、実際に確認済みの結果を分ける。新規設計や保存方法を維持する場合は、移行計画を無理に作らない。

HTMLなどの提示形式は必要に応じて選ぶ。形式の作り込みを目的にせず、リポジトリに残した資料から判断理由を読めることを優先する。
