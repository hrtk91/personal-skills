# データの持ち方を設計する

機能を追加するときに、今のデータの持ち方で困らないか確認する。変える必要があれば、理由と変更方法を残す。最初は簡単な作りでもよいが、何を省いたかと、どんな機能が増えたら困るかを説明できるようにする。

専門用語から説明を始めず、そのアプリで誰が何をすると、何が残り、何が変わるかを書く。必要な専門用語には、その場で具体的な意味を添える。

## 1. 何ができるようになる？

依頼と実際の利用例から、誰が何を読み、追加・変更・削除するかを整理する。たとえば「家族がそれぞれの端末で買い物済みにする」と書く。

- 再読み込み後にも残す必要がある情報と、その画面を開いている間だけ必要な情報を分ける。
- 誰のデータか、誰と共有するか、誰が操作できるかを確認する。ログインする人と、食事を用意する対象者などを同じものと決めつけない。
- 編集途中、確定した内容、履歴、作り直せる検索結果などを区別する。同じ情報を複数持つなら、どれを元の情報として使い、他をいつ更新するかを決める。

今回の操作が触るデータを対象にする。画面の見た目だけの変更で保存方法を再検討したり、無関係なデータを全点検したりしない。

## 2. 今の保存方法で困ることはある？

既存の設計記録と、その操作から保存・読み出しまでの実装を確認する。新規設計なら、以下を設計する問いとして使う。

- 一つずつ区別するID、持ち主、所属先は分かるか。後で分けても、それらと項目の意味を復元できるか。
- 別々の操作が同じデータを丸ごと保存していないか。二人が同時に操作したら、変更が消えるか、不必要に拒否されるか。
- まとめて成功・失敗させる必要がある変更は何か。途中だけ保存されると何が困るか。
- 何をどんな形式で保存するかが、画面の状態を表す型だけで決まっていないか。画面変更が保存形式へ波及しない境界と、読み書き時の値の検証があるか。
- 型の宣言、実行時の検証、DBの制約はそれぞれ何を防いでいるか。型やテストの存在だけで、保存時の保証があると判断しない。
- JSON内部の検索・結合・個別更新が必要になったか。配列の位置やキャッシュキーの文字列だけに、識別子や所属の意味が埋まっていないか。

項目の名前だけで用途を推測しない。読み書きする箇所を根拠にし、確認できたことと未確認を分ける。説明がないことと、不要なデータであることを区別する。

## 3. どこを変えればよい？

問題ごとに「今のままでよい」「説明を補う」「保存方法や更新処理を変える」を選び、理由を書く。変更する場合は、今回の要求によって以前のどの前提が成立しなくなったかを示す。

たとえば、買い物チェックと献立編集が独立した操作なら、別々に保存できる案を検討する。ただし、テーブルを分けるだけで同時操作の問題が解決するとは限らない。更新処理、古い画面からの操作の判定、まとめて保存する範囲も確認する。

JSONを一律に禁止したり、将来の可能性だけで細かく分割したりしない。丸ごと読み書きする小さな設定はJSONのままでもよい。反対に、スキーマ変更を避けるためだけに、何でも入る汎用項目へ押し込めない。実際の参照・更新方法と必要な保証から判断する。

簡単な作りを残すなら、識別子・所属・意味を失わず、独立した操作の入口を区別できるようにする。「後で直す」だけで済ませず、「家族が個別に更新するようになったら一括保存を見直す」など、再検討する具体的な変化を残す。保存形式のバージョンは、古い形式の判別や移行に必要な場合に設ける。

## 4. 何を残し、どう確かめる？

[設計記録の項目](references/design-record.md)を使い、対象範囲の既存資料を更新する。記録がなければ、リポジトリの文書配置に合わせて作る。図だけで終えず、利用例から判断理由を読めるようにする。

既存データがある変更では、変更前後の対応、残すデータ、移行できない値の扱い、切り替えと失敗時の復旧方法を必要な範囲で決める。検証は「二人の変更が両方残る」「移行後も持ち主と内容が変わらない」など、実際の結果を対象にする。

設計依頼では、案と検証方針までを成果物にする。実装も依頼されている場合は、今回必要な変更と確認まで進める。無関係な整理は後続へ分ける。

次の機能追加では、この記録の見直し条件と今回の要求を照合する。条件に当てはまれば関連部分を再評価し、当てはまらなければ全体を再設計しない。

## 他のスキルとの分担

このスキルは、データの持ち方を選び直して理由を残すところを担当する。必要な場合に、現状の業務ルール調査は `investigating-domain`、処理の責務や依存方向は `backend-development-principles`、案の独立審査は `design-review`、具体的なテスト作成は `test-design` を使う。毎回すべてを起動する手順にはしない。
