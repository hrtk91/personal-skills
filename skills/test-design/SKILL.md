# テスト設計

テストを、実装の動きを記録するものではなく、必要な契約の破壊を検出するものとして設計する。

## 手順

1. 変更理由、利用者または呼び出し側、変更前後の処理を確認する。
2. 守る契約の根拠を、仕様、ADR、domain rule、port、外部契約、再現した不具合のいずれかから特定する。
3. 各テストの目的を次の形で一文にする。

   ```text
   対象は、条件または操作のとき、観測可能な結果を保証する。
   ```

4. その保証を最小の適切な境界で観測する。
5. Arrange / Act / Assertを分け、Actは原則として一つの振る舞いにする。
6. 対象コードを意図的に壊した場合にテストが失敗するか確認する。実際に破壊して試す場合は、別worktree、一時コピー、mutation toolなどへ隔離し、終了後に元の差分と一致することを確認する。

現在の変更で追加・変更された失敗経路と、変更の影響を受ける維持すべき既存契約を優先する。関連文書に書かれた全仕様を一度にテストへ変換せず、変更と無関係な広い契約や別境界の不足はfollow-up候補として分ける。

契約の根拠を説明できない場合は、テストを追加せず、仕様と利用箇所を調査する。一般的な実装パターン、ライブラリの慣習、存在する分岐だけを新しい仕様の根拠にしない。

## 境界の選び方

次の語彙を形式的に当てはめず、対象プロジェクトが実際に持つ境界へ対応付ける。

- 業務ルールや不変条件は、domainの公開APIから検証する。
- 処理順、権限、原子性などの業務フローは、usecaseの入出力と副作用から検証する。
- HTTP、DB、外部APIなどの変換責務は、adapterまたは外部契約の境界で検証する。
- migrationはSQLを実行できることではなく、対応対象の旧状態からupgradeして必要なデータ保証を満たすことを検証する。
- 複数境界をまたぐ利用者フローは、細かな異常系を重複させず、代表的な正常系をE2Eで検証する。

実装詳細しか観測できない場合は、より内側のテストを増やす前に、利用側が必要とする契約が存在するか確認する。

## テストケースの書き方

- テスト名または隣接する仕様記述から、対象、条件または操作、守る結果を読めるようにする。
- fault injectionの方法はArrangeの説明に置き、テスト目的として扱わない。
- エラー系は、エラー分類だけでなく、失敗を隠さないこと、途中状態を残さないことなど、契約上必要な結果を検証する。
- fixtureは、所有者、権限、状態、既存データなど、結果を左右する前提が読める名前にする。
- 内部関数の呼び出し回数や中間表現ではなく、公開された結果または永続化された状態を優先して検証する。
- 一つのテストへ複数の目的を詰め込まない。失敗時のエラー変換とrollbackなど、独立して壊れる保証は分ける。
- 呼び出し回数は、重複実行や副作用の有無が契約である場合だけ検証する。

避ける例:

```text
存在しないschemaを参照するとエラーを返す
migrationを実行すると補完用の行が追加される
```

これらは障害の作り方や実装結果しか示さず、守る契約が分からない。

契約が存在する場合の例:

```text
永続化に失敗すると、公開処理は失敗を隠さず永続化エラーを返す
旧バージョンからupgradeすると、既存データも新しい必須制約を満たす
```

## 追加前の確認

- その振る舞いを必要とする現在の利用者または処理がある。
- 仕様の根拠と、テストが失敗させる回帰を説明できる。
- Assertが目的の保証を直接観測している。
- 同じ保証を別のテストが既に十分に検証していない。
- 今回の差分を元へ戻す、または変更した失敗経路を壊すと失敗する。変更外の広い不足は必須テストと混ぜない。
- 実装を固定しすぎず、許容される別実装でも通る。
- テスト名、仕様記述、fixture、Assertが同じ目的を示している。

## 報告

追加・変更したテストごとに、守る契約、根拠、検証境界、主なAssertを簡潔に報告する。必須、既存テストで十分、follow-up候補、追加不要を分ける。追加しなかった候補は、仕様根拠がない、重複する、今回の変更外、別境界で検証済みなどの理由を示す。
