# テスト設計

テストは、現在のコードと同じ動きを書き写すものではない。利用者や呼び出し側が頼っている振る舞いが壊れたときに、失敗して知らせるものとして作る。

## このskillで使う言葉

- **守る振る舞い**: 利用者や呼び出し側が頼ってよい振る舞い。入力に対する戻り値、HTTP status、保存結果、エラー時に途中データを残さないことなど。一般に「契約」とも呼ぶ。
- **根拠**: その振る舞いを守る必要がある理由。仕様書、ADR、公開インターフェース、外部APIの仕様、確認済みの不具合など。
- **確認する場所**: どこから対象を呼び、どこに現れた結果を見るか。一般に「テスト境界」とも呼ぶ。
- **外から確認できる結果**: 戻り値、HTTP response、保存されたデータ、外部サービスへの送信など。内部変数やprivate関数の途中結果ではない。

## 手順

1. なぜ変更するのか、誰または何が結果を使うのか、変更前後で何が変わるのかを確認する。
2. 今回追加・変更する守る振る舞いと、変更の巻き添えで壊れるおそれがある既存の振る舞いを挙げる。
3. 各振る舞いについて、守る必要がある根拠を探す。根拠が見つからなければ、すぐにテストを書かず、仕様と利用箇所を調べる。
4. 各テストの目的を次の形で一文にし、その内容がテスト名だけで分かる名前を付ける。

   ```text
   対象は、条件または操作のとき、外から確認できる結果を保証する。
   ```

5. 一つの入口の契約を確認するテストか、複数の操作をつなぐscenarioかを決める。名前、配置、実行単位をその粒度に合わせる。
6. 目的の結果を実際に作る処理から最も近く、その結果を直接確認できる入口を選ぶ。たとえばHTTP statusを守るなら、statusへ変換する処理を通して確認する。
7. Arrange（前提とテストデータ）、Act（対象の実行）、Assert（結果の確認）を分ける。Actは原則として一つにする。
8. 修正を一時的に元へ戻すか対象処理を壊す。失敗したAssertとメッセージを見て、防ぎたい不具合のためにテストが失敗したことを確認する。実際にコードを壊して試す場合は、別worktreeまたは一時コピーを使い、作業中の変更を失わないようにする。

既存の振る舞いへの影響は、変更した関数を使う箇所、同じ条件分岐を通る処理、同じ変換処理を使う箇所から探す。関連文書にある全仕様を一度にテストへ変換せず、今回の変更と無関係な不足は後続課題に分ける。

一般的な実装パターン、ライブラリの慣習、コードに分岐が存在することだけを、新しい仕様の根拠にしない。

## 確認する場所の選び方

対象プロジェクトが実際に持つ入口と責務に合わせる。ディレクトリ名やアーキテクチャ用語だけで決めない。

- 計算や業務ルールは、そのルールを呼び出す公開関数から確認する。
- 処理順、権限、複数の保存をまとめて成功または失敗させる処理は、その一連の処理を開始する入口から、戻り値と最終状態を確認する。
- HTTP、DB、外部APIとの変換は、実際にその変換が行われる接点で確認する。
- migrationはSQLが実行できることだけでなく、変更前のデータを用意し、更新後に必要なデータが残ることを確認する。
- 複数の仕組みをまたぐ利用者の操作は、代表的な正常系だけをE2Eで確認する。細かなエラー条件は、それを扱う一番近い場所で確認する。

内部処理しか確認できない場合は、その処理自体を固定する前に、利用側が本当に必要としている結果を調べる。

## テストケースの書き方

- テスト名だけで、対象、条件または操作、守る結果が分かるようにする。隣接する説明文やテスト本体を読まないと目的が分からない名前にしない。
- 説明文の方がテスト名より明確なら、説明文の内容を縮めずテスト名へ反映する。内部用語や短いラベルへ言い換えて意図を失わせない。
- テスト名や目的に複数の結果を書いたら、それぞれに対応するAssertがあるか確認する。名前に「イベントを保存する」と書きながら、イベント件数しか確認しない状態にしない。
- 保存物や送信内容は、存在や件数だけで十分か、識別子、種類、関連先、順序、状態、主要な内容まで必要かを、守る振る舞いから決める。全fieldを機械的に固定せず、値が違うと別の意味になる項目を確認する。
- 監査記録や業務イベントでは、対象、種類、発生順、実行者、業務上必要な内容などが正しくなければ、行が存在しても目的を満たさない。必要な項目を分けてAssertする。
- 障害を起こす手段はArrangeの説明に置き、テストの目的や名前にしない。
- エラー系は、エラーの種類だけでなく、失敗を成功扱いしないことや、途中状態を残さないことなど、必要な結果を確認する。
- テストデータは、所有者、権限、状態、既存データなど、結果を左右する前提が名前から分かるようにする。
- private関数の呼び出し回数や途中のデータではなく、戻り値や最終的に保存された状態を優先して確認する。
- 一つのテストへ複数の目的を詰め込まない。別々に壊れる可能性がある振る舞いはテストを分ける。
- 呼び出し回数は、重複実行を防ぐこと自体が必要な振る舞いである場合だけ確認する。

外部サービスやWidgetとの統合では、該当する失敗点を先に列挙し、どの境界がそれぞれを検出するか対応付ける。

- 入力: 空値、形式違反、過大入力、期限切れ
- 利用準備: SDKやscriptの読込失敗、初期化失敗
- 通信: timeout、接続失敗、HTTPとしての失敗
- 応答: decode失敗、外部サービスによる拒否、期待する識別子や用途との不一致
- ライフサイクル: 再実行、遅れて届くcallback、cleanup、画面離脱

すべてをE2Eへ集めず、失敗を分類または状態へ反映する最も近い境界で確認する。利用者に見える代表的な結果だけを、必要に応じて上位の境界でも確認する。

保存結果そのものを守る場合は、書き込み処理の戻り値だけでなく、実際の保存先から最終状態を読む。DBならケース用DBへqueryし、対象行と必要な内容を確認する。書き込み側と同じdecoderや変換処理を共有する場合も、読み取れたことだけで成功にせず、重要な値を独立した期待値と比較する。同じ誤りを共有してテストが通るおそれがあるなら、保存先を直接読むテスト用queryを使う。

## テスト群の分け方

- ファイル名、module名、suite名は、実際に確認する対象と粒度を表す。
- 一つの入口の契約を確認するテストと、複数の操作を順番につなぐscenarioを同じものとして扱わない。
- runnerは実行対象の選択と順序を担当し、個々の契約を確認するAssertやテストデータ作成を持たない。
- fixtureはテストの前提を準備する。テストが守る結果のAssertは、目的を記述したテスト側へ置く。
- 共通処理を曖昧な名前の置き場へ集めない。HTTP clientや設定など、具体的な責務が分かる名前にする。
- 単独実行と一括実行は同じテストケースを呼び出し、検証内容を重複させない。

## テスト基盤の性質を確認する

並列性、隔離、resourceの後始末など、テスト基盤自体の性質も守る振る舞いとして扱う。

- 並列実行は、同時実行数の設定や全件成功だけで確認しない。複数ケースが同時に到達したことをbarrierなどで確認する。
- 非干渉は、共有していれば競合する同じ主キー、同じファイル名、同じport、同じ障害注入対象などを使い、各ケースが成功することで直接確認する。
- 並列処理を直列化すると成功するテストは、並列実行の保証にならない。
- 外部resourceを複数取得する場合は、後続resourceの取得を失敗させ、先行resourceが解放された結果を確認する。
- cleanupは呼び出し回数だけでなく、process、container、DB、lock、一時ファイルなどが実際に残っていない結果を優先して確認する。

避ける例:

```text
存在しないschemaを参照するとエラーを返す
migrationを実行すると補完用の行が追加される
```

これらは、障害を起こす手段や現在の実装結果を説明しているだけで、何を守るかが分からない。

目的が分かる例:

```text
永続化に失敗すると、公開処理は失敗を隠さず永続化エラーを返す
変更前のデータをmigrationすると、必要なデータを失わず新しい形式へ移行できる
```

## 追加前の確認

- その振る舞いを必要とする現在の利用者、呼び出し側、または処理がある。
- 守る根拠と、テストで防ぎたい不具合を説明できる。
- Assertが目的の結果を直接確認している。
- テスト名や目的に書いた各結果へAssertが対応し、存在や件数だけでは意味を確認できない保存物の主要項目も検証している。
- 説明文とテスト本体を隠してテスト名だけを読んでも、前提、操作、期待結果を説明できる。
- 同じ対象、条件、結果を別のテストが既に直接確認していない。
- 修正を元へ戻すか失敗経路を壊すと、テストが失敗する。
- 同じ結果を実現する別の正しい実装へ変えても、テストは通る。
- テスト名、説明、テストデータ、Assertが同じ目的を示している。

## 報告

追加・変更したテストごとに、守る振る舞い、その根拠、確認した場所、主なAssertを簡潔に報告する。候補は「今回必須」「既存テストで十分」「後続課題」「追加不要」に分ける。追加しなかった候補には、根拠がない、重複する、今回の変更外、別の場所で確認済みなどの理由を付ける。
