# 影響範囲レビュー

目的は、変更された契約や前提を古いまま信じる箇所を残さないこと。関連しそうなコードを広く読むこと自体は目的にしない。

## 手順

### 1. 変更された契約・前提を明文化する

関数、型、設定、schema、永続化形式、外部APIなどについて、呼び出し側や利用側が依存していた前提がどう変わったかを書く。

単なる名前変更でも、旧名を参照する箇所が残らないことを確認対象にする。

### 2. 定義元と全利用箇所を検索する

変更対象の定義と参照を利用可能な検索手段で列挙する。renameや置換では旧名と新名の両方を検索する。

この検索はcoverage確保のため必須とし、差分が小さいことを理由に省略しない。利用可能ならbuild、型検査、構文検査、testも追従漏れの検出に使う。

### 3. 本当にその前提へ依存する箇所だけを追う

検索結果ごとに、変更された契約へ依存しているかを判断する。単に同じsymbolを参照しているだけで挙動や前提が変わらない箇所は、その根拠を確認して深掘りを止める。

依存する箇所は、入口から結果まで一つの経路として追う。特に次の追従を確認する。

- 呼び出し元と依存の組み立て
- 同じ機能へ到達する別の入口
- 保存形式、schema、既存データ
- mock、fixture、seed、test
- 環境ごとの設定や既定値
- 公開API、外部連携、利用者向け文書

認証・認可、resource lifetime、異常系などは、それらの契約が今回変わった場合だけ対象にする。テスト自体の品質評価は `review-test-quality` に任せる。

### 4. 影響境界で止める

変更を変換・adapter・境界処理で吸収し、その先の契約が変わっていないことを確認できたら、それより内側へ探索を広げない。

停止するときは「どの境界で何が吸収され、以降の前提が変わらないか」を説明できること。

## 指摘条件

次の場合だけ指摘する。

- 古い契約や前提へ依存する箇所が残っている
- 変更が別の入口、環境、保存データ、外部契約へ伝播していない
- 互換性や移行条件を満たせない
- 影響が閉じていると判断する根拠が不足している

今回の変更と無関係な既存問題や、単なる改善案は混ぜない。

## 報告

指摘ごとに、根拠となるファイルと行、変更された契約、追従漏れがある依存経路、起きる影響、最小の修正案を返す。重大度は親 `review` の基準に従う。

問題がなければ、確認した主な契約と影響境界を簡潔に示して「問題なし」と返す。
