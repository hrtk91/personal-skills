# 探索オーケストレーション

親スレッドを探索の実行者ではなく、状態管理と判断を担うオーケストレーターとして運用する。

## 基本原則

- 親スレッドは、目的、成功条件、制約、確認済みの事実、仮説、判断、未解決事項を維持する。
- 実際の調査、ログ解析、実験、実装、テストは、役割に適したsubagentへ委譲する。
- 親スレッドはユーザー要求、重要な設計資料、既存方針を把握し、判断責任を手放さない。
- subagentの報告を結論として扱わず、証拠を確認し、必要に応じて原典をスポットチェックする。
- 長い会話や生ログを引き継がず、次の探索に必要な状態だけを圧縮する。
- 事実、推測、判断、未確認事項を混同しない。

このモードは通常のsubagent活用を置き換えない。単純な読み取り、一度で終わる確認、一つの責務に閉じた局所修正には起動しない。一方、作業時間が短くても、複数ファイルを横断して各ファイルを数十行程度変更する場合、複数の契約を同時に保つ場合、設計判断と実装を別担当に渡す場合は起動する。subagentを呼ぶこと自体を目的にせず、独立した判断・実装・検証を委譲する利益がある場合に使う。

通常作業として開始した後も、変更が複数ファイルへ広がり各ファイルを数十行程度変更する見込みになった時点、二つ目の独立した調査・実装サイクルへ進む前、対象が別のIssue・PR・worktreeへ広がる前、context compaction後の再開時に、このモードへ切り替える必要がないか再評価する。切り替える場合は、その時点の事実と未解決事項から`現在地メモ`を初期化し、それ以前の会話をそのまま引き継がない。

## 親スレッドの責務

親スレッドは次を行う。

1. 探索の目的、成功条件、対象範囲、変更権限を確定する。
2. `現在地メモ`を初期化し、探索中は唯一の現在地として更新する。
3. 次に減らすべき不確実性を一つ選ぶ。
4. 利用可能なagent枠を確認し、独立して実行可能な探索課題をsubagentへ渡す。
5. 報告の証拠、再現性、矛盾、対象範囲を評価する。
6. 必要なら別subagentへ反証、再現確認、レビューを依頼する。
7. 確認できた結果だけを`現在地メモ`へ統合する。
8. 継続、分岐、方針変更、終了を判断する。

親スレッドは原則として、大量のコード読解、ログ全量解析、仮説ごとの実験、実装作業を直接行わない。ただし次は自身で行う。

- ユーザー要求と重要な制約の解釈
- 設計判断に必要な原典の確認
- subagentが示した証拠のスポットチェック
- agent間の矛盾解消
- 破壊的操作、外部変更、探索範囲拡大の判断
- 最終的な結論とユーザーへの報告

subagentを利用できない場合は、黙って通常作業へ切り替えない。このモードを継続できないことを伝え、通常モードへ移るかユーザーに確認する。

## 役割分担

モデル名ではなく、未確定な判断、意味的な難しさ、変更権限の順で実行担当を選ぶ。実効モデルとsandboxは、現在のagent metadataと設定で確認する。

| 課題 | 契約の状態 | 変更権限 | 担当 |
| --- | --- | --- | --- |
| 問題設定、設計判断、責務や不変条件の確定 | 前提判断が残る | read-only | 高判断能力の`architect` |
| 探索的・敵対的・高リスクレビュー | 契約や成立経路を疑う | read-only | 高判断能力の`reviewer` |
| 定義、利用箇所、ログなどの原典収集 | 問いと証拠形式は確定 | read-only | `explorer`。最終判断は任せない |
| 複数箇所へ波及する意味的に難しい実装 | 設計契約は確定 | workspace-write | 高推論の実装担当。実効設定がwrite可能なら`luna-worker` |
| rename、定型追従、明確な局所修正 | 手順、範囲、結果が確定 | workspace-write | `worker` |
| 観点が固定された定型レビュー | 観点と証拠形式が確定 | read-only | read-onlyの定型レビュー担当。利用可能なら`routine-reviewer` |
| 最終差分と受入条件の判定 | 完了候補 | 親が検証 | 親スレッド |

未確定な設計判断があれば実装担当へ渡さず、先に`architect`等で契約を閉じる。設計済みでも、複数の型・契約・失敗経路を同時に保つ必要があれば高推論の実装担当を使う。作業手順を機械的に説明できるなら`worker`を使う。重大度や差分量だけで高能力agentへ切り替えない。

親スレッドが短時間で安全に終えられる局所修正や、subagent成果の単純な統合には委譲を必須としない。実装量や判断事項が想定を越えたら止め、境界の明確な課題へ分け直す。

レビューは人数を先に決めず、リスクから必要な観点を決める。通常は一つの統合レビューから始め、独立した反証が必要な高リスク領域だけ追加する。同じ差分へ多数のreviewerを並列投入しない。

## 現在地メモ

開始時と各探索サイクルの終了時に、次の形式で状態を更新する。過去のメモを継ぎ足さず、現在の状態へ置き換える。

```markdown
## 探索の現在地

### 目的と成功条件
- 

### 探索で守るべき制約
- 

### 確認済みの事実
- 事実 — 証拠:

### 現在の判断
- 判断 — 根拠:

### 有効な仮説
- 仮説 — 支持する根拠 — 反証条件:

### 棄却した仮説
- 仮説 — 棄却理由 — 再検討条件:

### 未解決事項
- 

### 実行計画
- task_id / attempt — 課題 — 担当agent / agent ID — worktree — baseline — writer — 選定理由 — checkpoint — 状態 — 完了条件:

### 次の探索
- 課題 — 完了条件:
```

圧縮時にも、探索で守るべき制約、否定結果、棄却理由、判断を覆す条件、未解決事項、未完了の実行計画と担当境界を消さない。詳細な時系列や生ログは現在地メモへ入れず、必要なら証拠の場所だけを残す。

長期保存や別セッションへの引き継ぎが必要な場合は、[exploration-state.md](assets/exploration-state.md)を作業場所へコピーして更新する。保存場所は既存のリポジトリ方針に従い、方針がなければユーザーに確認する。

## Subagentへの依頼

subagentには親スレッドの会話全文を渡さない。現在地メモから、課題の実行に必要な情報だけを切り出す。

```markdown
## 探索課題
何を明らかにするか。

## 背景
なぜ今この課題を調べるか。

## 確認済みの事実
今回必要な事実だけ。

## 検証する仮説
仮説と反証条件。

## 対象と制約
対象範囲、読み取り専用か、変更可能範囲、禁止事項。

## 完了条件
何が分かれば終了するか。

## 進捗確認
最初のcheckpoint、長時間処理中に変化する報告または成果物。成果物を残さない場合は、正常な無報告時間と状況確認を始める時点。

## 報告形式
- 結論
- 証拠と参照場所
- 実行した操作
- 観測結果
- 仮説を支持または反証する理由
- 未確認事項
- 次に調べる場合の候補
```

一つのsubagentへ複数の曖昧な問いをまとめない。互いに独立し、同じファイルを編集しない課題だけを並列化する。実装を伴う場合も、親スレッドは調査結果と変更対象を確定してから、上の役割分担に従って境界の明確な実装課題として委譲する。依頼には変更可能なファイル、禁止事項、必要なテスト、完了時に返す差分と証拠を含める。

agent階層を無制限に深くしない。原則として親スレッドだけが課題をdispatchし、実行担当はleaf agentとして再委譲しない。再委譲が必要な場合は、そのagentを中継役として明示し、子agent分を含む同時実行枠を事前に確保する。

### 実装を渡す契約

実装担当を起動する前に、次をすべて依頼へ含める。

- `task_id`と`attempt`
- 目的と、担当が所有する責務
- baseline、依存先、確認済みの前提
- 設計判断の引き渡し: 変更理由ごとの責務境界、失敗時の扱い、確認方法
- 守るべき不変条件
- 採用する設計と、採用しない方法
- 専用worktree、変更可能ファイル、唯一のwriter
- 受入コマンドと期待結果
- 進捗を確認できる成果物と最初のcheckpoint
- 停止・親への判断返却条件
- 完了報告の形式
- `VERIFIED_COMPLETE`判定時に使う受入チェック
  - 受入QC（指定コマンド）実行
  - 引き渡した設計判断との整合確認
  - 不変条件適合確認

一つでも未確定なら、実装担当へ推測させない。編集前に停止して不足する判断を返すよう指示し、親が設計課題として閉じる。複数agentに同じworktreeやファイルを同時編集させない。interrupt後の部分差分は自動で捨てず、親が再利用可否を判断する。

## Subagentの監視と完了確認

各attemptを次の状態で管理する。

```text
DRAFT -> READY -> RUNNING -> REPORTED_COMPLETE -> VERIFIED_COMPLETE
                    |                 |
                    v                 v
               SUSPECTED_STALL   REJECTED_ATTEMPT
                    |                 |
                    v                 v
               INTERRUPTING      attempt + 1
                    |
                    v
                 ABORTED
```

- 起動時にagent ID、attempt、baseline、worktree、writerを記録する。
- `wait`のtimeoutは失敗ではない。通常は定型作業を90秒、高推論実装を120秒程度の間隔で観測し、長いbuild等は契約で延ばす。
- `running`というstatusだけを進捗と数えない。新しい報告、diff、検証出力など、契約で定めた成果物の変化を確認する。
- checkpoint後に2回連続で報告と成果物の両方が変化しなければ、状況確認を`send_message`で一度だけ送る。さらに1監視間隔進捗がなければinterruptする。
- `SUSPECTED_STALL`で進捗を確認できたら`RUNNING`へ戻し、連続無進捗回数と状況確認済みフラグをリセットする。interrupt後に最終報告または終了statusを受け取ったら、再利用できる成果物を棚卸しして`ABORTED`または`REPORTED_COMPLETE`へ進める。
- completedはそのattemptの終端状態とする。同じ課題の矛盾や不足に対してfollow-upを積まず、圧縮した修正版契約を別agentの新attemptへ渡す。既存agentを別の独立した課題で再利用することまでは禁止しない。
- 完了報告は`REPORTED_COMPLETE`にすぎない。親が許可範囲の差分、未追跡ファイル、受入コマンド、報告との整合を原典から確認して初めて`VERIFIED_COMPLETE`にする。
- 親と別agentは、writerが編集中の共有worktreeへformatter、autofix、テストによる生成処理を同時実行しない。

## 報告の統合

subagentの報告を次の順序で評価する。

1. 完了条件に答えているか確認する。
2. 結論を支える具体的な証拠があるか確認する。
3. 事実と推測が分かれているか確認する。
4. 対象範囲外の変更や仮定が混ざっていないか確認する。
5. 他の報告や既知の事実と矛盾しないか確認する。
6. 重要な主張を原典でスポットチェックする。
7. 採用、不採用、追加確認が必要、のいずれかへ分類する。

証拠が足りない場合は、親スレッドが穴を推測で埋めない。実行中のagentには一度だけ追跡依頼できる。completed agentは終端状態なので、必要なら修正版契約を別agentの新attemptへ渡す。

## 終了条件

次をすべて満たした場合に探索を終了する。

- 成功条件に対する答えが得られた
- 主要な結論に確認可能な証拠がある
- 重大な矛盾が解消されている
- 未解決事項と対象外事項が明示されている
- 結論が成立する範囲と、覆る条件が説明できる
- 実装を含む場合は、要求された検証が完了している
- 実装を含む場合は、`VERIFIED_COMPLETE`で受入QCに加え、引き渡した設計判断と不変条件への適合を確認している

終了時は、最終的な現在地メモを基に、結論、根拠、変更内容、検証結果、残る不確実性をユーザーへ報告する。

## 避けること

- 親スレッド自身が探索へ没入し、状態更新を後回しにする
- 親スレッドが、委譲可能な実装やテストを理由なく引き取る
- リスクや観点を定めず、同じ差分へ多数のreviewerを投入する
- 会話全文や全ログをsubagentへ渡す
- subagentの結論を証拠確認なしで採用する
- 「失敗した」だけを記録し、条件や観測を残さない
- 棄却した仮説を無条件の永久決定として扱う
- 現在地メモへ時系列ログを追記し続ける
- agentが実行中のまま完了と報告する
