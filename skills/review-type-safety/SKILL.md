# 型安全性レビュー

1. 変更差分と、変更された型・関数の利用箇所を読む。
2. 次を確認する。
   - 型とデータ構造が制約を表し、不正な状態を作りにくい
   - 外部から入る値を信頼境界で検証している
   - 外部入出力用の表現と内部の業務上の型が区別され、変換箇所が明確である
   - 検証済みまたは業務上の型を文字列や数値へ戻し、実際の外部境界を越えないまま同じ意味の型へ作り直していない。避けられない場合は、制約や失敗情報を失わず同じ値へ戻ることを確認する
   - 入力、検証済みの値、業務上の値、保存・通信用の値など、意味の異なる段階を型または明示的な変換で区別している
   - schema、decoder、validatorなどの境界定義が提供側の変更に追従している
   - 暗黙の変換、型の強制、都合のよい既定値で不正値を隠していない
   - unchecked cast、強制unwrap、想定外入力によるpanicなど、検証を迂回する処理を増やしていない
   - 失敗が呼び出し側から識別でき、握りつぶされていない
   - 未指定、失敗、複数の業務状態を一つのnullや真偽値へ押し込めていない
   - 状態の分岐が網羅され、追加された状態の扱いが全利用箇所で明確である
   - 文書変更では、型名、設定名、コード参照、実装事実が原典と一致する
3. 指摘ごとに根拠となるファイルと行、想定される影響、修正案を返す。重大度は親reviewが統一基準で決める。問題がなければ「問題なし」と返す。
