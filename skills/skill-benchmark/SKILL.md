# Skill benchmark

skillは「良さそうな指示」を増やすのではなく、観測された失敗を減らせたときだけ改善とみなす。測定できない微調整を続けない。

## 手順

1. **失敗と仮説を一文にする**
   - 何が困るのか、skill変更で何が改善するはずかを書く。
   - 再現する失敗がなく、明確な合格条件も置けないなら変更を急がない。

2. **評価ケースを選ぶ**
   - 実運用で起きた失敗を優先する。
   - fixtureを新造する前に、既存repoのcommit/PRを固定して使えないか確認する。
   - 新規実装は空repoから開始してよい。
   - ケースには task、必須条件、悪化とみなす挙動、機械検査、人間評価を記録する。

3. **比較条件を固定する**
   - 同じモデル、推論設定、ツール権限、開始状態、taskを使う。
   - baselineとtreatmentで変えるのは対象skillだけにする。
   - モデル名・version・設定を結果へ残す。結果はその構成に対する評価とみなす。

4. **baseline / treatmentを実行する**
   - 既定は各3回。出力が安定している場合だけ減らす。
   - 実装結果は毎回cleanな開始状態から作る。
   - 評価前に、どちらがbaselineか分からない形で成果物を並べる。

5. **機械判定と人間判定を分ける**
   - build、test、要件、禁止された変更など決定的に判定できるものを先に確認する。
   - 不定形な品質は、絶対点より「A/Bのどちらを採用するか」のblind pairwiseを優先する。
   - review系では、見つけるべき問題の見逃しと、根拠の薄い指摘を別に数える。

6. **採否を決める**
   - 狙った失敗が改善し、重大な要件・既存ケースを悪化させない場合だけ採用する。
   - 差が曖昧なら、指示が少ないbaselineを残す。
   - 一つの低重要度な失敗だけから一般則を増やさない。同種の失敗が蓄積したらskillへ抽出する。

## 継続運用

- 日常利用で気になった出力は、まずbenchmark caseとして保存し、その場でskillへ一般化しない。
- skillを変更したら、対象ケースだけでなく小さなregression setも再実行する。
- モデルを変更したらsmoke caseを再実行し、skillなしでも改善しているなら不要になったskillを削る候補にする。
- benchmark自体の整備コストがskillの効果を上回らないよう、ケースは少数から始める。
