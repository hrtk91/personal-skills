# スキル文書から実行すべき確認を読み取れるようにする

状態: **比較完了・介入不採用**。利用者による比較では、番号付き手順を保った基準版が明確に選ばれた。ルール、兆候、直し方、理由へ一律に分ける介入は採用しない。

## 追加する理由

これは特定の実運用失敗を固定した評価ではない。スキル文書でルール、検出方法、理由、例外が混ざったとき、AIが実行時の確認事項を読み取りにくくなる可能性を調べる代表例として追加する。

## 目的

スキル文書を教科書のような長い説明にせず、AIが「何を見つけたら、どう直すか」を読み取れる形へ整理できるか評価する。

短いことだけを正解にしない。元のルール、例外、理由を失わず、実行時の確認が見つけやすいことを測る。

## 開始時に使うもの

- 原因の候補: `benchmarks/hypotheses/actionable-skill-instructions.md`
- 比較材料: `benchmarks/fixtures/actionable-skill-instructions/`
- 元のスキル文書: `source-skill.md`
- 条件ごとの依頼文: `prompts/baseline.md`、`prompts/separated-guidance.md`
- 変更後の形を確認する基準例: `comparisons/separated-guidance.md`
- 実行方法: 実行ごとに空の一時ディレクトリへ`source-skill.md`と`prompts/baseline.md`だけを渡し、基準版を生成する。次に、その基準版を`baseline-output.md`として、`prompts/separated-guidance.md`と一緒に別の担当へ渡す。変更条件には元文書、基準例、他条件の依頼文を見せない。

基準例は正解文ではない。見出しや表現の一致では採点しない。

## AIへ渡す依頼

`prompts/`の各文書をそのまま使用する。一つの実行へ複数の依頼文を混ぜない。

## 必ず満たす条件

全条件で次を満たす。

- [ ] 元文書にあるルール、例外、理由を失わない。
- [ ] 元文書にないルールを追加しない。
- [ ] 短くするために判断材料を削らない。

ルールと検出方法を分ける条件では次も満たす。

- [ ] ルール、直すべき兆候、直し方、理由を分ける。
- [ ] ルール本文を短く保つ。
- [ ] 直すべき兆候から、実行時に何を探すか分かる。
- [ ] 各兆候に対する直し方を見つけられる。
- [ ] 詳しい理由や例外がルール本文へ混ざっていない。

## 起きてほしくないこと

- 元文書を単に短く要約する。
- 理由や例外を削る。
- 見出しだけ分け、同じ長文を移動する。
- 正しい書き方を網羅しようとして、直すべき兆候が埋もれる。
- 基準例の文面をコピーする。

## 内容を機械的に確認する項目

```text
1. 元文書の各ルール、例外、理由が成果物に対応付く
2. 元文書にない義務を追加していない
3. 変更条件では、ルール、兆候、直し方、理由を別々に探せる
4. 各兆候から対応する直し方を辿れる
```

## 人が比較する項目

匿名化した二つの成果物を読み、次を優先する。

1. 実行時に探すべき兆候を早く見つけられる。
2. 兆候を見つけた後、直し方を迷わない。
3. 元の理由と例外が残っている。
4. 同程度なら短い方を選ぶ。

実行手順を扱う文書では、次も確認する。

5. 最初に行うことと実行順が分かる。
6. 番号付き手順の内訳が、段階ごとに読める。
7. 絶対に外せない確認と補助的な注意の強弱が分かる。
8. 見出しと手順番号が同じ階層を重複して表していない。
9. 一つの手順に複数の内訳がある場合、長い列挙ではなく下位の箇条書きで読める。
