# investigating-domainの目的保持と構造非依存性 / 2026-08-16

## 調べたこと

- 対象の失敗: Webアプリ固有の探索経路を外す際、業務ドメイン調査という目的まで一般的な実装調査へ広げてしまう。
- 期待した改善: プロジェクト構造を仮定せず業務知識を復元し、一般的な実行経路や障害経路の調査には誤適用しない。
- 固定ケース: `benchmarks/cases/investigating-domain-purpose-and-portability.md`

## 採用条件

- 正例の9要件を基準版より悪化させない。9件目は、個別概念より先にシステムと対象業務の全体像を示すこと。
- 負例では3回とも適用範囲外と判断する。
- 読みやすさは条件名を伏せた人手比較で別に確認し、自動採点だけで優劣を決めない。

## 実行条件

| | 基準版 | 変更版 |
| --- | --- | --- |
| モデル | gpt-5.6-luna | gpt-5.6-luna |
| 推論設定 | medium | medium |
| subagent | v2、fresh context | v2、fresh context |
| skill | `main`の旧版 | PR #39版 |
| 実行回数 | 正例3、負例3 | 正例3、負例3 |

各実行には対象のskill、task、fixtureだけを渡し、他runの出力や採点結果は渡していない。

## 結果

### 最初の正例: RuleShelfの業務知識復元

| 回 | 基準版 | 変更版 |
| --- | ---: | ---: |
| 1 | 8/9 | 8/9 |
| 2 | 8/9 | 8/9 |
| 3 | 8/9 | 8/9 |

当初は8要件をすべて満たしたため同点としていた。しかし、匿名化したA/Bを利用者へ提示したところ、両方とも「そもそもどういうシステムか」という前提を説明せず、型の説明から始まっていると指摘された。

この比較で読みやすさを選ぶ前提が崩れたため、最初のA/B比較は無効とした。「システムの目的と対象業務の位置づけを個別概念より先に示す」を9件目へ追加し、taskは変更せずskill側だけを修正した。

### 前提説明を追加した変更版の再実行

| 回 | 変更版 |
| --- | ---: |
| 1 | 9/9 |
| 2 | 9/9 |
| 3 | 9/9 |

3回とも、RuleShelfを社内規程を社員へ配信するサービスと説明してから、規程公開の位置づけ、個別概念、関係者、不変条件へ進んだ。事実誤認、未確認事項の断定、Web構造の強制、call path中心への逸脱は0件だった。

### 負例: SessionEnd queueの実行・障害経路

| 回 | 基準版 | 変更版 |
| --- | --- | --- |
| 1 | 誤って適用し、実装調査を実行 | 適用範囲外 |
| 2 | 誤って適用し、実装調査を実行 | 適用範囲外 |
| 3 | 誤って適用し、実装調査を実行 | 適用範囲外 |

前提説明を追加した後も変更版を3回再実行し、すべて適用範囲外と判断した。主目的が業務知識の復元ではないと識別し、代わりに実行経路、queue状態機械、失敗・回復経路、runtime artifactの調査が必要だと示した。

基準版は3回とも適用対象だと判断し、うち1回は実行上のSessionEndを「ユーザー操作の起点」と解釈した。これはWeb・ユースケース中心の旧記述が、業務ドメイン以外にも広く反応する回帰を示す。
