# 1つのPull Requestで求めるレビュー判断は1つにする

Pull Requestにする可能性がある変更では、この原則を常に適用する。

編集を始める前に、次の空欄を1文で埋める。

> レビュワーは、______してよいかを判断する。

今回含めることと含めないことも明示する。判断には、利用者から見える振る舞い、契約、または構造上の境界を書く。「依頼された改善がすべて正しいか」は1つの判断ではない。

作業中は、次の基準でscopeを確認する。

> ある変更を承認し、別の変更を却下しても矛盾しないなら、別のPull Requestにする。

依存する変更はfollow-upまたはstacked PRへ分ける。隣接する不具合、cleanup、rename、refactor、migration、文書不足、test不足を発見しても、それだけでは現在のPull Requestへ追加する理由にならない。現在のレビュー判断を成立させるために必須な場合だけ含める。

Pull Requestを作成・更新する前に、次を確認する。

1. すべての変更fileが、最初に定めた1つの判断へ必要か確認する。
2. 独立した承認が必要な変更を削除するか、別のPull Requestへ分ける。
3. PR本文の`## レビュワーに求める判断`には、箇条書きではなく1つの段落を書く。
4. 後続へ送った事項を`## 今回含めないこと`へ書く。

差分量は警告材料であり、判定基準ではない。複数layerを変更しても判断が1つの場合はあり、小さな差分でも複数の判断を含む場合がある。
